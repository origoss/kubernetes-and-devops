Session 3 · Observability · about 25 minutes · after the session

Install kube-prometheus-stack and meet its parts

Your win: the metrics stack runs on your kind cluster from one committed values file, and you can name every Pod in it. You can also say which parts Helm made and which parts the operator made.

Before this: you installed and removed a small chart with Helm in lesson 01, and you know what a CRD and a control loop are from lesson 02. Your kind cluster is running, and your Docker VM has at least 6 GB of memory. The example files are in the course repository, in examples/s3/, after a git pull.

What's in the box

kube-prometheus-stack is one Helm chart that installs a whole monitoring system: the Prometheus Operator, Prometheus, Alertmanager, and by default also Grafana, kube-state-metrics and node-exporter.[1] The operator is the heart of it. It "provides Kubernetes native deployment and management of Prometheus and related monitoring components".[2]

ComponentRuns asJobIn our values
Prometheus OperatorDeployment kps-operatorWatches the monitoring CRs. Writes Prometheus and Alertmanager config. Runs their StatefulSets.on
PrometheusStatefulSet, made by the operator from a Prometheus CRScrapes targets, stores time series, evaluates alert rules.on
AlertmanagerStatefulSet, made by the operator from an Alertmanager CRGroups, silences and routes the alerts Prometheus sends.on
GrafanaDeployment kps-grafana (plain Helm, no operator)The UI: dashboards and Explore.on
config-reloadersidecar container in the Prometheus and Alertmanager PodsNotices that the generated config changed and tells the server to reload it.on
Grafana sidecarstwo sidecar containers in the Grafana PodWatch for ConfigMaps that hold dashboards and datasources, and load them into Grafana.on
kube-state-metricsDeploymentTurns Kubernetes object state (replicas, restarts) into metrics.off
node-exporterDaemonSet, one Pod per nodeNode CPU, memory and disk as metrics.off

Why turn two parts off? Memory. Your whole cluster is one Docker container on your laptop, and today you only need metrics from your own apps. In a real cluster you keep both on: without them you have no node dashboards and no metrics about Deployments and Pods.

The values file, line by line

The chart has hundreds of default values. You override only the ones that matter, in one file you commit. It is short enough to read in full:

examples/s3/values-kps.yaml

# Slim kube-prometheus-stack for a laptop kind cluster.
fullnameOverride: kps
kubeStateMetrics:
  enabled: false
nodeExporter:
  enabled: false
# kind does not expose these control-plane endpoints; their targets would show as down.
kubeEtcd:
  enabled: false
kubeControllerManager:
  enabled: false
kubeScheduler:
  enabled: false
kubeProxy:
  enabled: false
prometheus:
  prometheusSpec:
    retention: 6h
    resources:
      requests: { cpu: 100m, memory: 400Mi }
      limits: { memory: 1Gi }
alertmanager:
  alertmanagerSpec:
    resources:
      requests: { cpu: 10m, memory: 32Mi }
      limits: { memory: 128Mi }
grafana:
  resources:
    requests: { cpu: 50m, memory: 128Mi }
    limits: { memory: 384Mi }
  • fullnameOverride: kps: short object names (kps-operator, kps-grafana). Without it, every name starts with kps-kube-prometheus-stack-.
  • kubeStateMetrics, nodeExporter: off, to save memory (see above).
  • kubeEtcd … kubeProxy: the chart would scrape these control-plane parts, but kind does not expose their metrics ports. You would only get four red "down" targets.
  • prometheus.prometheusSpec: goes, almost word for word, into the spec of the Prometheus custom resource. retention: 6h deletes data older than six hours, so the disk stays small. The resources are the requests and limits you met in session 1.
  • alertmanager.alertmanagerSpec, grafana.resources: the same idea for the other two servers.

Memory and wifi. This stack plus a small app used about 1.9 GiB inside the kind node when we measured it. Give your Docker VM at least 6 GB. The first install pulls about eight images, so do it at home on good wifi, not on the venue network.

Two layers: Helm, then the operator

Here is the surprise of this lesson. Helm does not create the Prometheus server. Helm creates a Prometheus custom resource: an object of a new kind that the chart taught the API server through a CRD.[3] The operator watches that object and deploys a StatefulSet for it.[4] It also writes Prometheus's whole configuration into a Secret, generated from the ServiceMonitor and PrometheusRule objects it finds.

INSTALL TIME: Helm, runs once                RUN TIME: the operator, loops forever

values-kps.yaml ─┐
chart templates ─┴─► helm ─► Prometheus CR ─────watch──► kps-operator (a Pod)
                       │     ServiceMonitors ───watch──►      │
                       │     Deployments: operator,           │ creates and keeps fixing
                       │       grafana                        ▼
                       │     ConfigMaps, Services   StatefulSet prometheus-kps-prometheus
                       ▼                            Secret prometheus-kps-prometheus
                     exits                            (the generated prometheus.yaml)

So the two layers have different jobs. Helm runs when you run it: it renders templates, sends the objects, and exits. The operator runs all the time: whenever a CR changes, it changes the real things to match. Change retention in your values file and run helm upgrade: Helm updates the CR, and the operator updates the StatefulSet. Add a ServiceMonitor with plain kubectl apply: Helm is not involved at all, and the operator still picks it up. That second path is the next lesson.

Do it

  1. Work in your own hello repository. Make a monitoring/ folder and copy the values file into it from the course repository. The command assumes you cloned kubernetes-and-devops next to your hello repository; adjust ../kubernetes-and-devops if yours lives elsewhere, and run git pull in it first.

    mkdir -p monitoring
    cp ../kubernetes-and-devops/examples/s3/values-kps.yaml monitoring/

  2. Add the chart repository, then install. Pin the chart version, as in lesson 01: the same command must give the same stack next month.[5]

    helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
    helm repo update
    helm upgrade --install kps prometheus-community/kube-prometheus-stack --version 93.4.1 \
  -n monitoring --create-namespace -f monitoring/values-kps.yaml --wait --timeout 10m

    It took 72 seconds on our Mac with the images already pulled. The first time, expect several minutes. --wait returns only when everything is ready.

    helm -n monitoring list
    Expected output (trimmed) 
    NAME  NAMESPACE   REVISION  ...  STATUS    CHART                         APP VERSION
kps   monitoring  1         ...  deployed  kube-prometheus-stack-93.4.1  v0.95.2

  3. Name every Pod.

    kubectl -n monitoring get pods
    Expected output (your hashes differ) 
    NAME                              READY   STATUS    RESTARTS   AGE
alertmanager-kps-alertmanager-0   2/2     Running   0          15s
kps-grafana-6c58789c7-vb7d5       3/3     Running   0          16s
kps-operator-7988b8464d-hs4gx     1/1     Running   0          16s
prometheus-kps-prometheus-0       2/2     Running   0          15s

    Read the READY column: it counts containers, so these Pods have sidecars. Prometheus and Alertmanager are 2/2: the server plus its config-reloader. Grafana is 3/3: Grafana plus two sidecars, grafana-sc-dashboard and grafana-sc-datasources. List them yourself:

    kubectl -n monitoring get pod prometheus-kps-prometheus-0 -o jsonpath='{.spec.containers[*].name}'
    Expected output 
    prometheus config-reloader

    The -0 at the end is the StatefulSet's numbering: a StatefulSet's Pods get stable names, not random hashes.

  4. The API server grew new nouns. In lesson 02 a fresh kind cluster had no CRDs at all. Now:

    kubectl get crd | grep monitoring.coreos.com
    Expected output (dates trimmed) 
    alertmanagerconfigs.monitoring.coreos.com   Namespaced   v1alpha1(storage)
alertmanagers.monitoring.coreos.com         Namespaced   v1(storage)
podmonitors.monitoring.coreos.com           Namespaced   v1(storage)
probes.monitoring.coreos.com                Namespaced   v1(storage)
prometheusagents.monitoring.coreos.com      Namespaced   v1alpha1(storage)
prometheuses.monitoring.coreos.com          Namespaced   v1(storage)
prometheusrules.monitoring.coreos.com       Namespaced   v1(storage)
scrapeconfigs.monitoring.coreos.com         Namespaced   v1alpha1(storage)
servicemonitors.monitoring.coreos.com       Namespaced   v1(storage)
thanosrulers.monitoring.coreos.com          Namespaced   v1(storage)

    Ten new kinds of object. kubectl get, describe and explain work on all of them, exactly as on Pods.

  5. The key reveal. Ask for the Prometheus server as an object:

    kubectl -n monitoring get prometheus,alertmanager
    Expected output 
    NAME                                              VERSION              DESIRED   READY   RECONCILED   AVAILABLE   AGE
prometheus.monitoring.coreos.com/kps-prometheus   v3.16.0-distroless   1         1       True         True        68s

NAME                                                  VERSION   REPLICAS   READY   RECONCILED   AVAILABLE   AGE
alertmanager.monitoring.coreos.com/kps-alertmanager   v0.35.0   1          1       True         True        68s

    The Prometheus server is a custom resource. RECONCILED True is the operator reporting that reality matches the spec. Now check who made what. First, the kinds Helm sent:

    helm -n monitoring get manifest kps | grep -E '^kind: (Deployment|StatefulSet|Prometheus|Alertmanager)$' | sort | uniq -c
    Expected output 
       1 kind: Alertmanager
   2 kind: Deployment
   1 kind: Prometheus

    No StatefulSet at all. Yet there are two:

    kubectl -n monitoring get deploy,statefulset
    Expected output (trimmed) 
    deployment.apps/kps-grafana    1/1
deployment.apps/kps-operator   1/1
statefulset.apps/alertmanager-kps-alertmanager   1/1
statefulset.apps/prometheus-kps-prometheus       1/1
    kubectl -n monitoring get statefulset prometheus-kps-prometheus -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}'
    Expected output 
    Prometheus/kps-prometheus

    The StatefulSet's owner is the Prometheus CR, not a Helm release. The operator made it. That is the two-layer picture above, seen from your terminal.

  6. Meet the CR you will write yourself in the next lesson, the ServiceMonitor. It says "scrape the Services with these labels, on this port". The schema came with the CRD, so explain works:

    kubectl explain servicemonitor.spec
    Expected output (trimmed) 
    GROUP:      monitoring.coreos.com
KIND:       ServiceMonitor
VERSION:    v1

FIELD: spec <Object>

DESCRIPTION:
    spec defines the specification of desired Service selection for target
    discovery by
    Prometheus.

FIELDS:
  attachMetadata	<Object>
  ...
  endpoints	<[]Object> -required-
  ...

    The chart already ships some, one per component it monitors, plus about 30 PrometheusRule objects full of ready-made alerts:

    kubectl get servicemonitor,prometheusrule -A
    Expected output (trimmed) 
    NAMESPACE    NAME
monitoring   servicemonitor.monitoring.coreos.com/kps-alertmanager
monitoring   servicemonitor.monitoring.coreos.com/kps-apiserver
monitoring   servicemonitor.monitoring.coreos.com/kps-coredns
monitoring   servicemonitor.monitoring.coreos.com/kps-grafana
monitoring   servicemonitor.monitoring.coreos.com/kps-kubelet
monitoring   servicemonitor.monitoring.coreos.com/kps-operator
monitoring   servicemonitor.monitoring.coreos.com/kps-prometheus

NAMESPACE    NAME
monitoring   prometheusrule.monitoring.coreos.com/kps-alertmanager.rules
monitoring   prometheusrule.monitoring.coreos.com/kps-config-reloaders
monitoring   prometheusrule.monitoring.coreos.com/kps-general.rules
...

  7. Which ServiceMonitors does this Prometheus actually read? Not all of them. Its CR has a selector:

    kubectl -n monitoring get prometheus kps-prometheus -o jsonpath='{.spec.serviceMonitorSelector}'
    Expected output 
    {"matchLabels":{"release":"kps"}}

    Only ServiceMonitors labelled release: kps count; the chart sets that up by default.[1] Remember this line. In the next lesson it will cost you a few confused minutes, on purpose.

  8. Open the Prometheus UI. Port-forward in a second terminal and leave it running:

    kubectl -n monitoring port-forward svc/kps-prometheus 9090:9090

    Browse to http://localhost:9090, then Status → Target health. Every pool is named after the ServiceMonitor that produced it: serviceMonitor/<namespace>/<name>/<endpoint>.

    The same list from the command line, if you have jq (optional): one line per pool, with the number of targets in front.

    curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | "\(.scrapePool) \(.health)"' | sort | uniq -c
    Expected output (all up) 
       1 serviceMonitor/monitoring/kps-alertmanager/0 up
   1 serviceMonitor/monitoring/kps-alertmanager/1 up
   1 serviceMonitor/monitoring/kps-apiserver/0 up
   2 serviceMonitor/monitoring/kps-coredns/0 up
   1 serviceMonitor/monitoring/kps-grafana/0 up
   2 serviceMonitor/monitoring/kps-kubelet/0 up
   2 serviceMonitor/monitoring/kps-kubelet/1 up
   2 serviceMonitor/monitoring/kps-kubelet/2 up
   1 serviceMonitor/monitoring/kps-operator/0 up
   1 serviceMonitor/monitoring/kps-prometheus/0 up
   1 serviceMonitor/monitoring/kps-prometheus/1 up

    Look at kps-coredns: one ServiceMonitor, two targets, because CoreDNS runs two Pods. Keep that in mind for the next lesson.

  9. Open Grafana. Its admin password is random and lives in a Secret. Read it from there:

    kubectl -n monitoring get secret kps-grafana -o jsonpath='{.data.admin-password}' | base64 -d; echo

    That prints 40 random characters. The user name is admin. This is how secrets look in practice: stored in the cluster, read when needed, never typed into a file you commit. Note that base64 is an encoding, not encryption: anyone who may read Secrets in this namespace may read the password.[6]

    kubectl -n monitoring port-forward svc/kps-grafana 3000:80

    Log in at http://localhost:3000 and open Dashboards. Nobody clicked those dashboards together. Each one is a ConfigMap with the label grafana_dashboard=1:

    kubectl -n monitoring get cm -l grafana_dashboard=1
    Expected output (trimmed) 
    NAME                                    DATA   AGE
kps-alertmanager-overview               1      14m
kps-apiserver                           1      14m
kps-cluster-total                       1      14m
kps-grafana-overview                    1      14m
kps-k8s-coredns                         1      14m
...

    The grafana-sc-dashboard sidecar watches for such ConfigMaps and loads them into Grafana. It is another small watch loop, the same idea as the operator in miniature.

  10. Open Alertmanager:

    kubectl -n monitoring port-forward svc/kps-alertmanager 9093:9093

    At http://localhost:9093 one alert is already firing: Watchdog. Nothing is broken. It fires all the time on purpose, as a dead man's switch: "this alert is always firing, therefore it should always be firing in Alertmanager".[7] If it ever stops, your alerting pipeline is broken.

  11. Commit the values file. It is the whole description of your stack: anyone can rebuild it with the one command from step 2.

    git add monitoring/values-kps.yaml
    git commit -m "Add kube-prometheus-stack values"

    Leave the stack running. The next lesson uses it. If you need the memory back, helm -n monitoring uninstall kps removes it, but the ten CRDs stay: Helm does not delete CRDs, so the chart's README tells you to remove them by hand.[1]
