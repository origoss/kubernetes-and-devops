Why containers?

Your win: you can say in one sentence what a container is, and you have run two Python versions side by side without installing either.

Before this: the pre-flight check passed, so docker run hello-world works on your laptop.

The problem

Your server needs Python 3.13. Your classmate's needs 3.12. The production machine has 3.11 and a library version neither of you tested. "Works on my machine" is not a joke. It is what happens when a program depends on whatever happens to be installed around it.

A container solves this by shipping the program together with everything it expects to find: the runtime, the libraries, the files. That bundle runs the same on your laptop, a classmate's laptop and a cluster.[1]

What a container really is

A container is an ordinary process on a Linux machine, which the kernel fences in two ways:

  • Namespaces control what the process can see: its own process list, its own network, its own filesystem, its own hostname.[2]
  • cgroups control how much it can use: memory, CPU. Go over the memory limit and the kernel kills the process. You will meet this again in the fault hunt.[3]

There is no little computer inside. That is the key difference from a virtual machine.

On a Mac or Windows laptop? Containers need a Linux kernel, so Docker quietly runs a small Linux VM and your containers share its kernel. Check it yourself in step 4 below.

Images and containers

You already know this from programming: an image is the class, a container is an object. The image is a read-only package: files plus a note on what to run.[4] Every docker run creates a new container from it, each with its own process and its own scratch space. Images live in a registry; Docker Hub is the default one, and in lesson 05 you push to your own on GitHub.

Images follow an open standard, the OCI image format.[5] That is why an image you build with Docker runs unchanged in Kubernetes, which does not use Docker at all.

Do it

  1. Run two Python versions, one after the other. Nothing gets installed on your laptop.

    docker run --rm python:3.12-slim python --version
    docker run --rm python:3.13-slim python --version
    Expected output (the first run downloads ~200 MB) 
    Python 3.12.15
Python 3.13.16

    --rm deletes the container when it exits. The image stays, so the second run of each is instant.

  2. List the images you now have, the "classes":

    docker images python

  3. Look at the process list from inside a container:

    docker run --rm alpine ps
    Expected output 
    PID   USER     TIME  COMMAND
    1 root      0:00 ps

    Your laptop runs hundreds of processes, but the container sees exactly one: itself, as PID 1. That is a namespace at work.

  4. Compare kernels, inside and outside:

    uname -r
    docker run --rm alpine uname -r

    On Linux both lines match: one shared kernel. On a Mac or Windows the container reports a Linux kernel (something like 6.10.14-linuxkit), which belongs to Docker's hidden VM.
