Pod, Deployment, Service

Your win: you can say what a Pod really is on a node, why you run a Deployment instead of a bare Pod, and how labels and selectors tie a Deployment and a Service to their Pods. Your own k8s/deployment.yaml and k8s/service.yaml are applied, updated to a new version, rolled back, and committed to your repo.

Before this: your kind cluster is running, hello:0.1.0 is loaded into it (both from lesson 06), and you have the course repository from the pre-flight check. The first part runs from that kubernetes-and-devops folder, after a git pull: its example files are in examples/s1-07/. The second part runs in your own hello repository.

Pod: a set of containers that share a network

Kubernetes does not run containers directly. It runs Pods: one or more containers that are always scheduled together, onto the same node. Most Pods hold exactly one container.[1] What the containers of one Pod share, and what each keeps for itself:

In one Pod
Network: IP address, localhost, portsshared. One IP for the whole Pod; the containers reach each other on localhost, so two of them cannot both listen on 8080.
Volumesshared, if both containers mount them. An emptyDir volume is a scratch folder that lives exactly as long as the Pod.
Filesystemown. Each container sees its own image.
Processesown. Each container has its own process list, with its own PID 1.

Init containers run before the others, one after another, and each must finish successfully before the next starts. They prepare things: write a config file, wait for a database.[2]

On the node, a Pod starts as a sandbox: a tiny placeholder process (called pause) that holds the Pod's network namespace. The real containers join it. That is why the IP belongs to the Pod and not to any one container.

PID 1 is the container. Each container has one main process, PID 1. When it exits, the container has stopped. The kubelet then restarts that container, inside the same Pod, with the same IP and the same volumes; RESTARTS goes up by one. That is the Pod's restartPolicy: Always. But if the Pod itself is deleted, or its node dies, a bare Pod is gone for good: nothing recreates it.

Pod to Pod: a flat network

Each Pod gets its own IP from the cluster's network plugin, the CNI (Container Network Interface) plugin. In kind that is kindnet: you saw kindnet-cni in lesson 05. Whatever the plugin, Kubernetes demands one rule: every Pod can reach every other Pod by its IP, on any node, without address translation.[3] The catch: a replaced Pod gets a new IP. You cannot build on Pod IPs.

Deployment → ReplicaSet → Pod, held together by labels

A Deployment is where you write down what you want: "keep this many Pods from this template running".[4] It creates a ReplicaSet, whose only job is to keep the right number of matching Pods alive. One too few, and it creates one.[5] When you change the image, the Deployment makes a new ReplicaSet and shifts Pods over gradually; you will do that at the end of this lesson.

The selector is the important part. A ReplicaSet does not remember its Pods by name. Every time it looks, it counts the Pods whose labels match its selector. Change a Pod's labels and, to the ReplicaSet, that Pod no longer exists. Each Pod also records who made it in metadata.ownerReferences, so deleting a Deployment deletes its ReplicaSets and their Pods.[6]

Service: one stable address for changing Pods

A Service answers one question: "The Pods behind my app come and go with new IPs. Where do I send traffic?" It is an abstraction. It gets its own virtual IP, the ClusterIP, and a DNS name, its own name (hello). That IP belongs to no Pod and no machine. kube-proxy, on every node, sets up rules that forward traffic for it to whichever Pods currently match the Service's selector.[7]

The current list of those Pods lives in EndpointSlices: objects a controller keeps up to date as matching Pods appear, disappear or become ready.[8] A Service has two ports: port, where the Service listens (80), and targetPort, where your container listens (8080).

Your laptop is outside the cluster network, because kind runs the whole cluster inside a Docker container. kubectl port-forward opens a tunnel from a port on your laptop into the cluster, which is all you need for testing.[9]

Commands forget, files remember

You could create all of this with commands such as kubectl create or kubectl scale. But then the only record of what you want lives inside the cluster: nobody can review it, and you cannot rebuild it on a fresh cluster without remembering every flag. The declarative way is to write the desired state into files and let kubectl apply make the cluster match them. Run it once and it creates. Run it again with an edited file and it changes only what differs. Run it with nothing changed and it does nothing. The files go into git next to your code, so every change is reviewed and dated.[10]

Every object has the same four fields: apiVersion and kind say what it is, metadata names and labels it, and spec is what you want. The cluster adds a fifth, status: what it has actually reached. One rule about labels is checked by the API: a Deployment whose selector does not match its own template's labels would create Pods it can never count, and keep creating more, so it is refused outright.[4] A Service whose selector matches nothing is accepted, and simply has no endpoints.

Do it

A Pod, from a file

  1. Read the first example. It has the four fields every Kubernetes object has: apiVersion and kind say what it is, metadata names and labels it, and spec is what you want.

    examples/s1-07/pod.yaml
    apiVersion: v1
kind: Pod
metadata:
  name: hello
  labels:
    app: hello
spec:
  containers:
    - name: hello
      image: hello:0.1.0
      ports:
        - containerPort: 8080
    kubectl apply -f examples/s1-07/pod.yaml
    kubectl get pod hello -o wide --show-labels
    Expected output (trimmed) 
    pod/hello created
NAME    READY   STATUS    RESTARTS   AGE   IP           NODE                 ...   LABELS
hello   1/1     Running   0          4s    10.244.0.5   kind-control-plane   ...   app=hello

    ErrImagePull instead? The node does not have your image; that also happens after you recreate the cluster. Load it again with kind load docker-image hello:0.1.0, then kubectl delete pod hello and apply again.

  2. Ask the cluster for the whole object, as it stores it.

    kubectl get pod hello -o yaml
    Expected output (trimmed to the parts that matter today) 
    metadata:
  labels:
    app: hello
  name: hello
  namespace: default
  uid: 37d94c19-1e64-4913-a1d5-4099dba4f8e4
spec:
  containers:
  - image: hello:0.1.0
    imagePullPolicy: IfNotPresent
    name: hello
    ports:
    - containerPort: 8080
      protocol: TCP
  nodeName: kind-control-plane
  restartPolicy: Always
  terminationGracePeriodSeconds: 30
status:
  containerStatuses:
  - name: hello
    ready: true
    restartCount: 0
    user:
      linux:
        uid: 65532
  hostIP: 172.18.0.3
  phase: Running
  podIP: 10.244.0.5

    Three kinds of fields are mixed together here:

    • What you wrote: the name, the label, the image, the port.
    • Defaults the API filled in: imagePullPolicy: IfNotPresent (because the tag is not :latest), restartPolicy: Always, a 30-second grace period on shutdown.
    • What the cluster decided and observed: nodeName was set by the scheduler; everything under status is reported by the kubelet: the phase, the Pod's IP, the node's IP, the restart count, and the user your container runs as (65532, from lesson 04's USER).

  3. Try to change the running Pod: give it an environment variable.

    kubectl set env pod/hello GREETING=hi
    Expected output (trimmed) 
    error: ... Pod "hello" is invalid: spec: Forbidden: pod updates may not change fields other than `spec.containers[*].image`, ...

    A Pod is almost read-only once it exists. To change it, you delete it and create a new one. Keep that in mind: it is one reason nobody runs bare Pods for real.

Inside a Pod with several containers

  1. The second example has an init container and two app containers: your server, plus a busybox helper that just loops, so you have a shell to look around with. All of them mount the same emptyDir volume.

    examples/s1-07/pod-two.yaml
    apiVersion: v1
kind: Pod
metadata:
  name: two
spec:
  initContainers:               # run once, to completion, before the others start
    - name: init
      image: busybox:1.37
      command: ["sh", "-c", "echo 'written by the init container' > /shared/note.txt"]
      volumeMounts:
        - name: shared
          mountPath: /shared
  containers:
    - name: hello               # your server
      image: hello:0.1.0
    - name: sidecar             # a helper with a shell, so you can look around
      image: busybox:1.37
      command: ["sh", "-c", "trap 'exit 1' TERM; while true; do sleep 1; done"]
      volumeMounts:
        - name: shared
          mountPath: /shared
  volumes:
    - name: shared              # a scratch folder that lives as long as the Pod
      emptyDir: {}
    kubectl apply -f examples/s1-07/pod-two.yaml
    kubectl get pod two -w
    Expected output (stop the watch with Ctrl+C) 
    pod/two created
NAME   READY   STATUS            RESTARTS   AGE
two    0/2     Init:0/1          0          0s
two    0/2     PodInitializing   0          4s
two    2/2     Running           0          5s

    Init:0/1: zero of one init containers done. READY 2/2: both app containers run. The init container is not counted; it has finished.

  2. Look from inside the helper container (-c picks the container). Shared storage, shared network, separate processes:

    kubectl exec two -c sidecar -- cat /shared/note.txt
    kubectl exec two -c sidecar -- wget -qO- localhost:8080
    kubectl exec two -c sidecar -- ps
    Expected output 
    written by the init container
hello from my container
PID   USER     TIME  COMMAND
    1 root      0:00 sh -c trap 'exit 1' TERM; while true; do sleep 1; done
   21 root      0:00 sleep 1
   34 root      0:00 ps

    The file the init container wrote is there. localhost:8080 inside sidecar reaches your server in the other container: one network for the whole Pod. But ps does not show your server: each container has its own process list, and the helper's loop is its PID 1.

  3. See what a Pod is on the node. The node's container runtime lists Pods (sandboxes) and containers separately:

    docker exec kind-control-plane crictl pods --name two

    Copy the POD ID from the output into the next command:

    docker exec kind-control-plane crictl ps -a --pod 37403b2d4a902
    Expected output (trimmed; your IDs differ) 
    POD ID              CREATED          STATE    NAME   NAMESPACE   ...
37403b2d4a902       28 seconds ago   Ready    two    default     ...

CONTAINER       IMAGE           CREATED          STATE     NAME      ATTEMPT   POD ID          ...
54256905205e7   a69dd915c8355   24 seconds ago   Running   hello     0         37403b2d4a902   ...
3053f16e07344   ad4f11f7c85f8   24 seconds ago   Running   sidecar   0         37403b2d4a902   ...
1a0814f2dbd24   ad4f11f7c85f8   27 seconds ago   Exited    init      0         37403b2d4a902   ...

    One sandbox, three containers in it. The init container is Exited: it did its job and stopped. The sandbox holds the network, so the containers can come and go while the Pod keeps its IP.

  4. Kill a container's PID 1, the way a crash would, and see what survives.

    kubectl exec two -c sidecar -- kill 1
    kubectl get pod two -o wide
    kubectl get pod two -o jsonpath='{range .status.containerStatuses[*]}{.name} {.restartCount}{"\n"}{end}'
    kubectl exec two -c sidecar -- cat /shared/note.txt
    Expected output (trimmed) 
    NAME   READY   STATUS    RESTARTS     AGE   IP           ...
two    2/2     Running   1 (3s ago)   28s   10.244.0.6   ...
hello 0
sidecar 1
written by the init container

    The helper's PID 1 exited, so its container stopped, and the kubelet started a fresh one. Only that container restarted: your server's count is still 0. Same Pod, same IP, and the emptyDir file is still there. kubectl describe pod two shows the dead run under Last State: Terminated, Exit Code: 1.

    Why the trap in the helper's command? The kernel protects a namespace's PID 1: a signal reaches it only if the process has a handler for that signal. Without the trap, kill 1 would do nothing. Your Go server's runtime has a handler for SIGTERM, which is how Kubernetes stops it (step 12 below).

  5. Pod to Pod. Get the IP of the first Pod, hello, and call it from inside two (use your IP):

    kubectl get pod hello -o wide
    kubectl exec two -c sidecar -- wget -qO- 10.244.0.5:8080
    Expected output (trimmed) 
    NAME    READY   STATUS    RESTARTS   AGE   IP           ...
hello   1/1     Running   0          62s   10.244.0.5   ...
hello from my container

    Any Pod reaches any Pod by IP. Now delete hello and confirm that a bare Pod stays gone:

    kubectl delete pod hello
    kubectl get pods
    Expected output 
    pod "hello" deleted from default namespace
NAME   READY   STATUS    RESTARTS      AGE
two    2/2     Running   1 (90s ago)   2m

    Nothing will bring hello back, and its IP is gone with it. Keep two: you will use it as a client in a moment.

Your own Deployment

From here on you write your own manifests, for your own server, in your own repository. Switch to your hello repository folder (where main.go is) for the rest of the lesson. Leave the Pod two running: it will be your client inside the cluster.

  1. Let kubectl show you the shape of a Deployment without creating anything. --dry-run=client means "do not send it", and -o yaml prints what it would have sent.

    kubectl create deployment hello --image=hello:0.1.0 --dry-run=client -o yaml
    Expected output 
    apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: hello
  name: hello
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hello
  strategy: {}
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
      - image: hello:0.1.0
        name: hello
        resources: {}
status: {}

    The four fields again, an empty status, and a template: the Pod spec you know from pod.yaml, wrapped inside. The {} lines are empty placeholders you can drop. Use this trick whenever you forget the shape of an object, but write your own file: typing it is how the structure sticks.

  2. Create k8s/deployment.yaml: two replicas, and the containerPort your server listens on.

    k8s/deployment.yaml
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello          # the Pods this Deployment counts as its own
  template:               # the Pod to stamp out, replicas times
    metadata:
      labels:
        app: hello        # must match the selector above
    spec:
      containers:
        - name: hello
          image: hello:0.1.0
          ports:
            - containerPort: 8080

    Indent with spaces, never tabs. In YAML, indentation is the structure. containerPort is documentation: it does not open or change any port. Your server decides that through PORT.

    kubectl apply -f k8s/
    kubectl get deploy,rs,pod --show-labels
    Expected output (the hash suffixes differ) 
    deployment.apps/hello created
NAME                    READY   UP-TO-DATE   AVAILABLE   AGE   LABELS
deployment.apps/hello   2/2     2            2           5s    app=hello

NAME                              DESIRED   CURRENT   READY   AGE   LABELS
replicaset.apps/hello-7dd649b7d   2         2         2       5s    app=hello,pod-template-hash=7dd649b7d

NAME                        READY   STATUS    RESTARTS      AGE   LABELS
pod/hello-7dd649b7d-gz8xv   1/1     Running   0             5s    app=hello,pod-template-hash=7dd649b7d
pod/hello-7dd649b7d-lg7lh   1/1     Running   0             5s    app=hello,pod-template-hash=7dd649b7d
pod/two                     2/2     Running   1 (40s ago)   90s   <none>

    One file, three kinds of objects. The names give the chain away: hello → hello-7dd649b7d → hello-7dd649b7d-gz8xv. And the Pods carry a label you never wrote, pod-template-hash.

  3. Look at the selectors and the owners (use your own names).

    kubectl get rs -o wide
    kubectl get pod hello-7dd649b7d-gz8xv -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'
    kubectl get rs hello-7dd649b7d -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}{"\n"}'
    Expected output (trimmed) 
    NAME              DESIRED   CURRENT   READY   ...   IMAGES        SELECTOR
hello-7dd649b7d   2         2         2       ...   hello:0.1.0   app=hello,pod-template-hash=7dd649b7d
ReplicaSet/hello-7dd649b7d
Deployment/hello

    The ReplicaSet's selector is your selector plus pod-template-hash, a hash of the Pod template. That extra label keeps the Pods of an old and a new version apart during an update. The owner references point upward: Pod → ReplicaSet → Deployment.

  4. Watch self-healing. Start a watch in one terminal:

    kubectl get pods -l app=hello -w

    In a second terminal, delete one of the Pods (use a name from your list):

    kubectl delete pod hello-7dd649b7d-gz8xv
    Expected output (the watch terminal, trimmed) 
    NAME                    READY   STATUS    RESTARTS   AGE
hello-7dd649b7d-gz8xv   1/1     Running   0          22s
hello-7dd649b7d-lg7lh   1/1     Running   0          22s
hello-7dd649b7d-gz8xv   1/1     Terminating   0          25s
hello-7dd649b7d-ztk9j   0/1     Pending       0          0s
hello-7dd649b7d-ztk9j   0/1     ContainerCreating   0          0s
hello-7dd649b7d-gz8xv   0/1     Error               0          25s
hello-7dd649b7d-ztk9j   1/1     Running             0          1s

    The replacement ztk9j was Pending in the same instant the old Pod started Terminating, and running within a second. The ReplicaSet counted the Pods matching its selector, found one where it wants two, and made one: the controller loop from lesson 05, live. -l app=hello filters by label, exactly as the selector does. Stop the watch with Ctrl+C.

    Why does the old Pod say Error on its way out? Kubernetes stops a container by sending its PID 1 the SIGTERM signal. Your server does not handle that signal itself, so the Go runtime ends it with a non-zero exit code. That is harmless here; the homework fixes it.

Your own Service, and its EndpointSlice

  1. Create k8s/service.yaml and apply the whole folder again.

    k8s/service.yaml
    apiVersion: v1
kind: Service
metadata:
  name: hello
  labels:
    app: hello
spec:
  selector:
    app: hello            # send traffic to every Pod with this label
  ports:
    - port: 80            # the Service listens here
      targetPort: 8080    # your container listens here
    kubectl apply -f k8s/
    kubectl get service hello
    kubectl get endpointslices -l kubernetes.io/service-name=hello
    kubectl get pods -l app=hello -o wide
    Expected output (trimmed; your IPs differ) 
    deployment.apps/hello unchanged
service/hello created
NAME    TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)   AGE
hello   ClusterIP   10.96.54.26   <none>        80/TCP    0s
NAME          ADDRESSTYPE   PORTS   ENDPOINTS               AGE
hello-qjgfz   IPv4          8080    10.244.0.7,10.244.0.9   0s
NAME                    READY   STATUS    RESTARTS   AGE   IP           ...
hello-7dd649b7d-lg7lh   1/1     Running   0          60s   10.244.0.7   ...
hello-7dd649b7d-ztk9j   1/1     Running   0          35s   10.244.0.9   ...

    apply only created what was new: the Deployment was unchanged. The ENDPOINTS are exactly your two hello Pods, on the target port. two is not there; it has no app=hello label. The CLUSTER-IP belongs to none of them.

  2. Use the Service the way other Pods do: by name. From inside two:

    kubectl exec two -c sidecar -- wget -qO- hello
    kubectl exec two -c sidecar -- nslookup hello.default.svc.cluster.local
    Expected output (trimmed) 
    hello from my container
Server:		10.96.0.10
Name:	hello.default.svc.cluster.local
Address: 10.96.54.26

    The name hello resolves to the ClusterIP (the full name is <service>.<namespace>.svc.cluster.local), and port 80 there reaches one of your Pods on 8080.[11] The DNS server at 10.96.0.10 is CoreDNS, the Pods you described in lesson 06.

  3. Now from your laptop. Open a tunnel from your port 8080 to the Service's port 80. This command keeps running, so leave it there.

    kubectl port-forward service/hello 8080:80

    In a second terminal:

    curl localhost:8080/
    Expected output (first terminal, then second) 
    Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080
Handling connection for 8080

hello from my container

    Open http://localhost:8080/ in your browser too: your code, in your image, running in Kubernetes. Stop the tunnel with Ctrl+C.

    Notice -> 8080. Port-forward to a Service picks one of its Pods and connects straight to it. It is a testing tool, not a load balancer. Port 8080 already in use? Pick another local port: kubectl port-forward service/hello 9090:80.

  4. Break the selector. In k8s/service.yaml, change the selector to app: helo (one letter missing), then apply and look.

    kubectl apply -f k8s/
    kubectl get endpointslices -l kubernetes.io/service-name=hello
    kubectl exec two -c sidecar -- wget -qO- -T 3 hello
    Expected output 
    deployment.apps/hello unchanged
service/hello configured
NAME          ADDRESSTYPE   PORTS     ENDPOINTS   AGE
hello-qjgfz   IPv4          <unset>   <unset>     9s
wget: can't connect to remote host (10.96.54.26): Connection refused
command terminated with exit code 1

    No error anywhere when you applied it. The Service exists, its name and ClusterIP still work, but no Pod matches app=helo, so the EndpointSlice is empty and every connection is refused. kubectl port-forward service/hello would wait 60 seconds and then give up with error: timed out waiting for the condition. When a Service does not answer, check its endpoints first. Fix the typo, apply again, and check that both IPs are back:

    kubectl apply -f k8s/
    kubectl get endpointslices -l kubernetes.io/service-name=hello
    Expected output 
    deployment.apps/hello unchanged
service/hello configured
NAME          ADDRESSTYPE   PORTS   ENDPOINTS               AGE
hello-qjgfz   IPv4          8080    10.244.0.7,10.244.0.9   15s

  5. The selector from the Pod's side. Change one Pod's label (use your own name), then look at everything:

    kubectl label pod hello-7dd649b7d-lg7lh app=debug --overwrite
    kubectl get pods -o wide --show-labels
    kubectl get endpointslices -l kubernetes.io/service-name=hello
    Expected output (trimmed) 
    pod/hello-7dd649b7d-lg7lh labeled
NAME                    READY   STATUS    ...   AGE    IP            ...   LABELS
hello-7dd649b7d-bn9d6   1/1     Running   ...   3s     10.244.0.10   ...   app=hello,pod-template-hash=7dd649b7d
hello-7dd649b7d-lg7lh   1/1     Running   ...   105s   10.244.0.7    ...   app=debug,pod-template-hash=7dd649b7d
hello-7dd649b7d-ztk9j   1/1     Running   ...   92s    10.244.0.9    ...   app=hello,pod-template-hash=7dd649b7d

    Read it carefully. The relabelled Pod lg7lh is still running, untouched. But the ReplicaSet counted only one Pod with app=hello, so it created bn9d6 within seconds. The Service did the same sum: its endpoints are now the two app=hello Pods, and 10.244.0.7 is out.   6. Clean up the extra Pods: the client two and the relabelled one.

    kubectl delete pod two hello-7dd649b7d-lg7lh

The file wins

  1. Apply once more, without changing anything:

    kubectl apply -f k8s/
    Expected output 
    deployment.apps/hello unchanged
service/hello unchanged

    Nothing differs, so nothing happens. You can run apply as often as you like.

  2. Now scale up by command, then apply the file again.

    kubectl scale deployment hello --replicas=3
    kubectl get deploy hello
    kubectl apply -f k8s/
    kubectl get deploy hello
    Expected output 
    deployment.apps/hello scaled
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   3/3     3            3           15s
deployment.apps/hello configured
service/hello unchanged
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   2/2     2            2           18s

    kubectl scale changed the cluster but not your file. That gap between what is running and what is written down is called drift.[12] The next apply quietly put it back to 2, and your third replica was gone. Changes made by command last only until the next apply.

    kubectl diff -f k8s/ shows drift before you apply: after the scale, it prints - replicas: 3 / + replicas: 2.

  3. Do it the declarative way instead. Edit k8s/deployment.yaml to say replicas: 3, then apply.

    kubectl apply -f k8s/
    kubectl get deploy hello
    Expected output 
    deployment.apps/hello configured
service/hello unchanged
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   3/3     3            3           22s

    Same result as kubectl scale, but now the file says it, the next apply keeps it, and git will remember it.

Ship a version, break it, roll back

  1. Ship a new version. Change the greeting in main.go to hello from version 0.1.1, then build it under a new tag and copy it into the cluster, as in lesson 06:

    docker build -t hello:0.1.1 .
    kind load docker-image hello:0.1.1

    In k8s/deployment.yaml, change image: hello:0.1.0 to image: hello:0.1.1. Preview, apply, and watch the rollout:

    kubectl diff -f k8s/
    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    Expected output (trimmed) 
    -      - image: hello:0.1.0
+      - image: hello:0.1.1
deployment.apps/hello configured
service/hello unchanged
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 1 old replicas are pending termination...
deployment "hello" successfully rolled out

    This is a rolling update: the Deployment starts new Pods and stops old ones a few at a time, so some Pods answer during the whole change.[13] It does that with a second ReplicaSet:

    kubectl get rs -l app=hello
    Expected output 
    NAME               DESIRED   CURRENT   READY   AGE
hello-646b86479c   3         3         3       1s
hello-7dd649b7d    0         0         0       21s

    The old ReplicaSet is kept, scaled to 0: that is what makes a rollback possible. Restart your port-forward (it was attached to a Pod that is now gone) and check: curl localhost:8080/ answers hello from version 0.1.1.

  2. Now ship a broken version. Pretend you mistyped the tag, and this time change it by command:

    kubectl set image deployment/hello hello=hello:0.1.2
    kubectl rollout status deployment/hello --timeout=30s
    kubectl get pods -l app=hello
    Expected output (the broken Pod flips between ErrImagePull and ImagePullBackOff) 
    deployment.apps/hello image updated
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
error: timed out waiting for the condition
NAME                     READY   STATUS             RESTARTS   AGE
hello-646b86479c-4d8gv   1/1     Running            0          33s
hello-646b86479c-fdz67   1/1     Running            0          34s
hello-646b86479c-t2bz8   1/1     Running            0          34s
hello-6d746f67f6-54f25   0/1     ImagePullBackOff   0          31s

    No image hello:0.1.2 exists, so the new Pod is stuck in ImagePullBackOff. The rollout stops there and waits: it never removes an old Pod before a new one is ready. Your three 0.1.1 Pods keep serving.

  3. Roll back. List the revisions, then undo the last one:

    kubectl rollout history deployment/hello
    kubectl rollout undo deployment/hello
    Expected output 
    deployment.apps/hello
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
3         <none>

Warning: resource deployments/hello was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead.
deployment.apps/hello rolled back

    The broken Pod is removed, and the Deployment is back on 0.1.1.[14] Read the warning: it says what this lesson keeps saying. set image and undo are commands, so the file did not see them. Here it ends well, because your file still says 0.1.1: kubectl diff -f k8s/ now prints nothing. In real work, undo is the emergency brake; the lasting fix goes into the file.

  4. Commit the manifests. They are now the source of truth for how your server runs.

    git add k8s/ main.go
    git commit -m "Add Kubernetes Deployment and Service, ship 0.1.1"
    git push

    Leave everything running for lesson 08.
