Your server, running in Kubernetes

Your win: your own image runs in Kubernetes, heals itself when you kill it, and answers in your browser. You built it all with three commands.

Before this: your kind cluster is running, hello:0.1.0 is loaded into it, and you can read a pod's Events (all from lesson 06).

Pod: the smallest thing Kubernetes runs

Kubernetes does not run containers directly. It runs Pods: one or more containers that share a network address and are always scheduled together. Most Pods hold exactly one container, as yours will.[1]

A Pod on its own is like docker run: if it dies or you delete it, nobody brings it back. Lesson 05 promised a controller that keeps the actual state equal to the desired state. A bare Pod has no such controller.

Deployment → ReplicaSet → Pod

A Deployment is where you write down what you want: "keep this many Pods from this template running".[2] It does not make Pods itself. It creates a ReplicaSet, whose only job is to keep the right number of matching Pods alive. One too few, and it creates one.[3] You will see all three objects in step 3, and their names give the chain away: hello → hello-6f4569fc87 → hello-6f4569fc87-7d8zn.

Why two layers? When you change the image, the Deployment makes a new ReplicaSet and shifts Pods over gradually. For today, one Deployment means one ReplicaSet.

Service: a stable address for changing Pods

Every new Pod gets a new name and a new IP. Something that talks to your server cannot chase those. A Service gives a set of Pods one stable name and one stable IP, and forwards traffic to whichever Pods currently match its selector.[4]

A Service has two ports. port is the one the Service itself listens on; we use 80, the usual HTTP port. targetPort is where the container listens, which for your server is 8080.

Your laptop is outside the cluster network, because kind runs the whole cluster inside a Docker container. kubectl port-forward opens a tunnel from a port on your laptop into the cluster, which is all you need for testing.[5]

Do it

  1. Run your image as a bare Pod, and check that your server started.

    kubectl run hello --image=hello:0.1.0
    kubectl get pods -o wide
    kubectl logs hello
    Expected output 
    pod/hello created
NAME    READY   STATUS    RESTARTS   AGE   IP           NODE                 ...
hello   1/1     Running   0          5s    10.244.0.8   kind-control-plane   ...
2026/10/06 08:34:43 listening on :8080

    The node pulled nothing. It already had hello:0.1.0, because you loaded it in lesson 06, and with a tag other than :latest the pull policy is IfNotPresent, so it uses that copy.[6] kubectl describe pod hello says so in its Events: Container image "hello:0.1.0" already present on machine.

    ErrImagePull instead? Run kubectl describe pod hello and read the Events. pull access denied for docker.io/library/hello means the node does not have your image. That happens after you recreate the cluster, too. Load it again with kind load docker-image hello:0.1.0, then kubectl delete pod hello and run it again.

  2. Now delete it, and look again.

    kubectl delete pod hello
    kubectl get pods
    Expected output 
    pod "hello" deleted from default namespace
No resources found in default namespace.

    Gone, for good. Wait as long as you like: nothing will bring it back, because nothing was watching it.

  3. Do the same with a Deployment, and list all three kinds of objects at once.

    kubectl create deployment hello --image=hello:0.1.0
    kubectl get deploy,rs,pod
    Expected output (the hash suffixes differ) 
    deployment.apps/hello created
NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/hello   1/1     1            1           5s

NAME                               DESIRED   CURRENT   READY   AGE
replicaset.apps/hello-6f4569fc87   1         1         1       5s

NAME                         READY   STATUS    RESTARTS   AGE
pod/hello-6f4569fc87-7d8zn   1/1     Running   0          5s

    Read the chain: the ReplicaSet wants 1 (DESIRED), has 1 (CURRENT), and 1 is ready. kubectl describe pod on the Pod shows Controlled By: ReplicaSet/hello-6f4569fc87.

  4. Delete the Pod again. Use your own Pod name.

    kubectl delete pod hello-6f4569fc87-7d8zn
    kubectl get pods
    Expected output 
    pod "hello-6f4569fc87-7d8zn" deleted from default namespace
NAME                     READY   STATUS    RESTARTS   AGE
hello-6f4569fc87-cdhhf   1/1     Running   0          1s

    Look at the name and the age. This is a new Pod, one second old. The ReplicaSet saw "desired 1, current 0" and made one. That is the controller loop from lesson 05, live.

  5. Put a Service in front of the Deployment. It listens on port 80 and forwards to port 8080 in the container.

    kubectl expose deployment hello --port=80 --target-port=8080
    kubectl describe service hello
    Expected output (trimmed; your IPs differ) 
    service/hello exposed
Name:                     hello
Selector:                 app=hello
Type:                     ClusterIP
IP:                       10.96.159.192
Port:                     <unset>  80/TCP
TargetPort:               8080/TCP
Endpoints:                10.244.0.10:8080
...

    Selector: app=hello is how the Service finds its Pods: kubectl create deployment gave them the label app=hello. Endpoints lists the Pod IPs it found, on the target port. Delete the Pod once more and the Endpoints line changes to the new Pod's IP, while the Service IP stays put.

  6. Open a tunnel from your laptop's port 8080 to the Service's port 80. This command keeps running, so leave it there.

    kubectl port-forward service/hello 8080:80

    In a second terminal:

    curl localhost:8080/
    curl localhost:8080/healthz
    Expected output (first terminal, then second) 
    Forwarding from 127.0.0.1:8080 -> 8080
Forwarding from [::1]:8080 -> 8080
Handling connection for 8080
Handling connection for 8080

hello from my container
ok

    Now open http://localhost:8080/ in your browser. That is your code, from your repo, in your image, running in Kubernetes. Stop the tunnel with Ctrl+C when you are done.

    Notice -> 8080 in the first line. Port-forward to a Service picks one of its Pods and connects straight to that Pod's target port. It is a testing tool, not a load balancer.

    Port 8080 already in use on your laptop? An old docker run may still hold it (docker ps). Or pick another local port: kubectl port-forward service/hello 9090:80 and curl localhost:9090/.

  7. Leave the Deployment and the Service running. Lesson 08 starts by deleting them and rebuilding both from files you write yourself.
