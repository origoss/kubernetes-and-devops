Your own web server

Your win: your own server answers on / and /healthz, on whatever port you give it in PORT, and its code is in your own GitHub repo.

Before this: the pre-flight check passed, so you have Go 1.27, git and a GitHub account.

The server you will ship

This small server is what you put in a container, push to a registry and run on Kubernetes for the rest of the course. It is 20 lines of Go and uses only the standard library.[1]

It has two endpoints. / is the "real" app, for people. /healthz is for machines: it answers ok when the process is alive. Later, Kubernetes asks exactly this question over and over, and restarts or stops routing to your container when it gets no answer.[2]

Patterns like "GET /healthz" name the HTTP method and the path. The standard router understands them since Go 1.22; any other method gets 405 Method Not Allowed.[3] The pattern "GET /" ends in a slash, so it matches every path no other pattern claims.

Configuration from the environment

The server reads its port from the PORT environment variable and falls back to 8080.[4] This is the twelve-factor rule: store config in the environment, not in the code.[5] You build the program once, and every place that runs it (your laptop, a container, a cluster) sets what differs from outside, without a rebuild. You will use exactly this with docker run -e PORT=… in lesson 03.

The twelve-factor app

That config rule is one of twelve. The Twelve-Factor App was written by Adam Wiggins in 2011 and last updated in 2017. It distils what the people behind the Heroku platform learned from running "hundreds of thousands of apps".[8] It predates Kubernetes, yet reads like a description of what Kubernetes expects from you. Here are the twelve, and where you meet each one in this course:

FactorThe ruleIn this course
I. CodebaseOne codebase in version control, many deploysyour one hello repo runs on your laptop, in kind and in CI
II. DependenciesDeclare and isolate dependencies explicitlygo.mod; the image bundles everything (lessons 03–04)
III. ConfigStore config in the environmentPORT, this lesson
IV. Backing servicesTreat databases, queues… as attached resourcesnot used: our server has none
V. Build, release, runStrictly separate build and run stagesbuild the image once, tag 0.1.0, run it anywhere (lesson 04); publish it and automate it in the session 2 pipeline
VI. ProcessesRun as stateless, share-nothing processeswhy three replicas just work (lesson 08)
VII. Port bindingExport services by binding to a portListenAndServe, no separate web server in front
VIII. ConcurrencyScale out by running more processesreplicas: 3 instead of a bigger machine (lesson 08)
IX. DisposabilityStart fast, shut down gracefully on SIGTERMKubernetes kills and replaces pods at will (lessons 07–08)
X. Dev/prod parityKeep development and production alikethe same image on your laptop, in kind and in CI; kind is real Kubernetes
XI. LogsTreat logs as event streamswrite to the output stream; docker logs, kubectl logs, and Loki in session 3
XII. Admin processesRun admin tasks as one-off processesa one-off kubectl run pod rather than logging into a server

Two factors are worth a closer look, because Kubernetes leans on them hardest. Processes (VI): a twelve-factor process keeps nothing it needs in memory or on local disk between requests.[9] That is what lets Kubernetes route any request to any replica, and throw a replica away without losing anything. Logs (XI): an app "should not attempt to write to or manage logfiles"; it writes its event stream, unbuffered, to stdout.[10] Collecting that stream is the platform's job. Our server's single log line goes through Go's default logger, which writes to standard error.[11] Docker and Kubernetes capture both output streams, so that is fine.

Our server is not perfect yet. It does not catch SIGTERM, so when Kubernetes stops it, requests still in progress are cut off instead of finishing. Disposability (IX) asks for a graceful shutdown.[12] You will see the symptom in lesson 08.

Want to use another language? You may, as long as your server listens on $PORT (default 8080) and answers GET / and GET /healthz. But every lesson shows Go, and on the day the instructor can only support Go.

Do it

  1. Make a folder and a Go module. The second command pins the Go version to 1.27, which matches the golang:1.27 image you build with in lesson 03.[6]

    mkdir hello && cd hello
    go mod init hello
    go mod edit -go=1.27

    go.mod (now)

    module hello

go 1.27

  2. Save this as main.go. Read it first: every line maps to a sentence above.

    main.go

    package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
)

func main() {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	http.HandleFunc("GET /", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello from my container")
	})
	http.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	log.Printf("listening on :%s", port)
	log.Fatal(http.ListenAndServe(":"+port, nil))
}

  3. Run it. It keeps running in this terminal.

    go run .
    Expected output 
    2026/10/06 00:26:17 listening on :8080

  4. In a second terminal, ask it both questions:

    curl localhost:8080/
    curl localhost:8080/healthz
    Expected output 
    hello from my container
ok

  5. Stop the server with Ctrl+C in the first terminal. Start it again on another port, set from outside:

    PORT=9090 go run .
    curl localhost:9090/healthz
    Expected output 
    2026/10/06 00:26:27 listening on :9090
ok

    Same code, different behaviour, no edit. Stop it again with Ctrl+C.

  6. Put it on GitHub. On github.com, create a new public repository called hello, with no README. Then, inside your hello folder (replace <you> with your GitHub username):

    git init -b main
git add go.mod main.go
git commit -m "Add hello web server"
git remote add origin https://github.com/<you>/hello.git
git push -u origin main

    GitHub asks for a token, not your password, when you push over HTTPS. If you already use SSH keys, use the SSH remote URL instead. Every later lesson adds files to this repo.

  7. Let your instructor review your work. In your repository on github.com, open Settings → Collaborators → Add people and enter your instructor's GitHub username, jagyugyaerik.[7] From now on, you submit every exercise as a pull request and request your instructor as the reviewer.
