Session 1 · Kubernetes · about 20 minutes · do it after the session

Write it down: your first manifests

Your win: k8s/deployment.yaml and k8s/service.yaml, written by hand for your own server, applied, scaled, self-healing, updated to a new version and rolled back, and committed to your repo.

Before this: lesson 07, so your hello Deployment and Service are running, created by commands.

Commands forget, files remember

In lesson 07 you told the cluster what to do, one command at a time. That works, but the only record of what you want now lives inside the cluster. Nobody can review it, and you cannot rebuild it on a fresh cluster without remembering every flag.

The declarative way is to write the desired state into files and let kubectl apply make the cluster match them. Run it once and it creates. Run it again with an edited file and it changes only what differs. Run it with nothing changed and it does nothing. The files go into git next to your code, so every change is reviewed and dated.[1]

Four fields, every time

Every Kubernetes object you write has the same skeleton:[1]

  • apiVersion and kind: which type of object. A Deployment is apps/v1, a Service is plain v1.
  • metadata: at least a name, usually some labels.
  • spec: the state you want.

There is a fifth, status, but you never write it. The cluster fills it in with the state it has actually reached.

Labels hold it all together

Objects find each other by labels, not by name. A Deployment has a selector that says "my Pods are the ones labelled app: hello", and a Pod template that stamps that same label on every Pod it creates. If the two disagree, the Deployment would create Pods it can never count as its own, and keep creating more. So the API refuses such a Deployment outright.[2]

The Service uses the same trick: its selector picks every Pod labelled app: hello, whoever made it. Here a mismatch is not refused. You simply get a Service with nobody behind it.[3]

Do it

Work in the root of your app repo.

  1. Delete the objects you made by command in lesson 07, so the files start from a clean slate.

    kubectl delete deployment,service hello
    Expected output 
    deployment.apps "hello" deleted from default namespace
service "hello" deleted from default namespace

  2. Let kubectl show you the shape of a Deployment without creating anything. --dry-run=client means "do not send it", and -o yaml prints what it would have sent.

    kubectl create deployment hello --image=hello:0.1.0 --dry-run=client -o yaml
    Expected output 
    apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: hello
  name: hello
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hello
  strategy: {}
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
      - image: hello:0.1.0
        name: hello
        resources: {}
status: {}

    Find the four fields, and the empty status. The {} lines are empty placeholders you can drop. Use this trick whenever you forget the shape of an object, but write your own file: typing it is how the structure sticks.

  3. Create k8s/deployment.yaml. Two replicas, and the containerPort your server listens on.

    k8s/deployment.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello          # "my Pods are the ones labelled app: hello"
  template:               # the Pod to stamp out, replicas times
    metadata:
      labels:
        app: hello        # must match the selector above
    spec:
      containers:
        - name: hello
          image: hello:0.1.0
          ports:
            - containerPort: 8080

    Indent with spaces, never tabs. In YAML, indentation is the structure. containerPort is documentation: it does not open or change any port. Your server decides that through PORT.

  4. Create k8s/service.yaml.

    k8s/service.yaml

    apiVersion: v1
kind: Service
metadata:
  name: hello
  labels:
    app: hello
spec:
  selector:
    app: hello            # send traffic to Pods with this label
  ports:
    - port: 80            # the Service listens here
      targetPort: 8080    # your container listens here

  5. Apply the whole folder, and look at what you got.

    kubectl apply -f k8s/
    kubectl get deploy,rs,pod,svc -l app=hello
    Expected output 
    deployment.apps/hello created
service/hello created
NAME                    READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/hello   2/2     2            2           5s

NAME                              DESIRED   CURRENT   READY   AGE
replicaset.apps/hello-7dd649b7d   2         2         2       5s

NAME                        READY   STATUS    RESTARTS   AGE
pod/hello-7dd649b7d-ml2pb   1/1     Running   0          5s
pod/hello-7dd649b7d-vltzz   1/1     Running   0          5s

NAME            TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)   AGE
service/hello   ClusterIP   10.96.145.194   <none>        80/TCP    5s

    -l app=hello filters by label, the same way the selectors do. Now apply a second time, without changing anything:

    kubectl apply -f k8s/
    Expected output 
    deployment.apps/hello unchanged
service/hello unchanged

  6. Check it answers, exactly as in lesson 07: port-forward in one terminal, curl in another, Ctrl+C when done.

    kubectl port-forward service/hello 8080:80
    curl localhost:8080/healthz
    Expected output (second terminal) 
    ok

  7. Now see why the file has to win. Scale up by command, then apply the file again.

    kubectl scale deployment hello --replicas=3
    kubectl get deploy hello
    kubectl apply -f k8s/
    kubectl get deploy hello
    Expected output 
    deployment.apps/hello scaled
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   3/3     3            3           15s
deployment.apps/hello configured
service/hello unchanged
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   2/2     2            2           18s

    kubectl scale changed the cluster but not your file. That gap between what is running and what is written down is called drift.[4] The next apply quietly put it back to 2, and your third replica was gone. Imperative changes last only until the next apply.

    kubectl diff -f k8s/ shows the drift before you apply: after the scale, it prints - replicas: 3 / + replicas: 2.

  8. Do it the declarative way instead. Edit k8s/deployment.yaml to say replicas: 3, then apply.

    kubectl apply -f k8s/
    kubectl get deploy hello
    Expected output 
    deployment.apps/hello configured
service/hello unchanged
NAME    READY   UP-TO-DATE   AVAILABLE   AGE
hello   3/3     3            3           22s

    Same result as kubectl scale, but now the file says it, the next apply keeps it, and git will remember it.

  9. Watch self-healing. Start a watch in one terminal:

    kubectl get pods -l app=hello -w

    In the second terminal, delete one Pod (use a name from your list):

    kubectl delete pod hello-7dd649b7d-j2cv8
    Expected output (the watch terminal, trimmed) 
    NAME                    READY   STATUS    RESTARTS   AGE
hello-7dd649b7d-j2cv8   1/1     Running   0          3s
hello-7dd649b7d-ml2pb   1/1     Running   0          22s
hello-7dd649b7d-vltzz   1/1     Running   0          22s
hello-7dd649b7d-j2cv8   1/1     Terminating   0          6s
hello-7dd649b7d-85cl2   0/1     Pending       0          0s
hello-7dd649b7d-85cl2   0/1     ContainerCreating   0          0s
hello-7dd649b7d-j2cv8   0/1     Error               0          6s
hello-7dd649b7d-85cl2   1/1     Running             0          0s

    The replacement 85cl2 was Pending in the same instant the old Pod started Terminating, and running within a second. Stop the watch with Ctrl+C.

    Why does the old Pod say Error on its way out? Kubernetes stops a container by sending it the SIGTERM signal. Your server does not handle that signal, so it dies with a non-zero exit code. That is harmless here.

  10. Ship a new version. Change the greeting in main.go to hello from version 0.1.1, then build it under a new tag and copy it into the cluster, as in lesson 06:

    docker build -t hello:0.1.1 .
    kind load docker-image hello:0.1.1

    In k8s/deployment.yaml, change image: hello:0.1.0 to image: hello:0.1.1. Preview, apply, and watch the rollout:

    kubectl diff -f k8s/
    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    Expected output (trimmed) 
    -      - image: hello:0.1.0
+      - image: hello:0.1.1
deployment.apps/hello configured
service/hello unchanged
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 1 old replicas are pending termination...
deployment "hello" successfully rolled out

    This is a rolling update: the Deployment starts new Pods and stops old ones a few at a time, so some Pods answer during the whole change.[5] It does that with a second ReplicaSet:

    kubectl get rs -l app=hello
    Expected output 
    NAME               DESIRED   CURRENT   READY   AGE
hello-646b86479c   3         3         3       1s
hello-7dd649b7d    0         0         0       21s

    The old ReplicaSet is kept, scaled to 0: that is what makes a rollback possible. Restart your port-forward (it was attached to a Pod that is now gone) and check: curl localhost:8080/ answers hello from version 0.1.1.

  11. Now ship a broken version. Pretend you mistyped the tag, and this time change it by command:

    kubectl set image deployment/hello hello=hello:0.1.2
    kubectl rollout status deployment/hello --timeout=30s
    kubectl get pods -l app=hello
    Expected output 
    deployment.apps/hello image updated
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
error: timed out waiting for the condition
NAME                     READY   STATUS             RESTARTS   AGE
hello-646b86479c-4d8gv   1/1     Running            0          33s
hello-646b86479c-fdz67   1/1     Running            0          34s
hello-646b86479c-t2bz8   1/1     Running            0          34s
hello-6d746f67f6-54f25   0/1     ImagePullBackOff   0          31s

    No image hello:0.1.2 exists, so the new Pod is stuck in ImagePullBackOff. The rollout stops there and waits: it never removes an old Pod before a new one is ready. Your three 0.1.1 Pods keep serving.

  12. Roll back. List the revisions, then undo the last one:

    kubectl rollout history deployment/hello
    kubectl rollout undo deployment/hello
    Expected output 
    deployment.apps/hello
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
3         <none>

Warning: resource deployments/hello was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. Consider using 'kubectl apply' with your previous configuration file instead.
deployment.apps/hello rolled back

    The broken Pod is removed, and the Deployment is back on 0.1.1.[6] Read the warning: it says what this lesson keeps saying. set image and undo are commands, so the file did not see them. Here it ends well, because your file still says 0.1.1: kubectl diff -f k8s/ now prints nothing. In real work, undo is the emergency brake; the lasting fix goes into the file.

  13. Commit the manifests. They are now the source of truth for how your server runs.

    git add k8s/ main.go
    git commit -m "Add Kubernetes Deployment and Service, ship 0.1.1"
    git push

    Leave everything running for lesson 09.
