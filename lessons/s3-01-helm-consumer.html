Session 3 · Helm · about 20 minutes · do it before the session

Install someone else's app with Helm

Your win: you installed, upgraded, rolled back and removed an app you did not write, driven by one small values file you can commit to git. You can say where Helm turns a chart into YAML, and where it keeps its history.

Before this: session 1 and session 2. Your kind cluster runs (kind create cluster if you deleted it), and you have the course repository; run git pull in it, because this lesson's example file is in examples/s3/.

Why a package manager

In session 1 you wrote two objects by hand: a Deployment and a Service. That was fine for one small server. In the session you install a monitoring stack called kube-prometheus-stack. Even trimmed down to fit on a laptop, it is 84 objects: Deployments, Services, ConfigMaps, Secrets, access rules, thirty sets of alerting rules, plus ten new kinds of object. Nobody kubectl applys that by hand, and nobody wants to upgrade it by hand next month.

You need four things: the objects packed together, a few knobs you can turn, a version you can upgrade and roll back, and a clean way to remove all of it. That is what Helm, the package manager for Kubernetes, gives you. Today you only use packages other people wrote. Writing your own is a separate skill.

Four words

WordWhat it is
chartThe package: templates for "all of the resource definitions needed to run an application", plus default settings.[1]
valuesThe settings. The chart ships defaults in its values.yaml; you override only what you need, in your own file.
release"An instance of a chart running in a Kubernetes cluster."[1] It has a name you choose. Install the same chart twice with two names and you get two releases.
repositoryWhere charts are published. Classic repositories are plain web servers. Charts can also live in an OCI registry, the same kind of registry that holds images, so ghcr.io from session 2 can store charts too.[2]

How it works

Helm is a program on your laptop. It "runs on your local machine and talks to the Kubernetes API server", exactly like kubectl, with the same kubeconfig.[1] Nothing Helm-specific runs in the cluster.

chart templates  ──┐
default values   ──┼──►  helm, on YOUR laptop  ──►  plain YAML  ──►  kube-apiserver
your values file ──┘     fills in the templates     Deployment,          │
                                                     Service, ...         │
                                                                          ▼
                                                    the same objects you wrote by hand
                                                    + one Secret per revision:
                                                      sh.helm.release.v1.<name>.v<N>
  1. Helm takes the chart's templates, the chart's default values and your values file, and fills in the templates. This rendering happens on your laptop. helm template does only this step and prints the result: "Render chart templates locally and display the output."[3]
  2. The result is plain Kubernetes YAML: the same Deployments and Services you wrote yourself in lesson 07. Helm sends them to the kube-apiserver, and from there everything works as you already know.
  3. Helm writes down what it did. By default, "release information is stored in Secrets in the namespace of the release", one Secret per revision, named sh.helm.release.v1.<name>.v<N>.[4] Each one holds that revision's record: the chart, the values you supplied, and the rendered YAML. That record is what helm history lists and what helm rollback goes back to.

Every install, upgrade or rollback adds a revision. "The first revision number is always 1", and each change adds 1.[5] A rollback does not rewind the counter: it creates a new revision whose content is copied from an old one.

One command, every time

helm install fails if the release exists; helm upgrade fails if it does not. helm upgrade --install does the right one: "if a release by this name doesn't already exist, run an install".[6] So the first install and every later change use the same command. Like kubectl apply, it is safe to run again: unchanged values give the same objects.

And the values go in a file, not on the command line. You could type --set replicaCount=3, but then the only record of your choice is your shell history. A file in git is reviewed, dated, and gives the same release on a fresh cluster. It is the same rule as lesson 07: commands forget, files remember.

Do it

  1. Install Helm. On macOS:

    brew install helm

    On Linux or Windows, follow the official Installing Helm page.[7] Then check the version:

    helm version
    Expected output (your patch version may be newer) 
    version.BuildInfo{Version:"v4.3.0", GitCommit:"v4.3.0", GitTreeState:"clean", GoVersion:"go1.26.8", KubeClientVersion:"v1.37"}

    You need Helm 4: the version must start with v4. Older blog posts show Helm 3 or even Helm 2; most commands are the same, but a few flags changed.

  2. Add the repository of podinfo, a tiny demo web app that exists for exactly this kind of practice. Then search it.

    helm repo add podinfo https://stefanprodan.github.io/podinfo
    helm search repo podinfo
    Expected output 
    "podinfo" has been added to your repositories
NAME           	CHART VERSION	APP VERSION	DESCRIPTION
podinfo/podinfo	6.17.0       	6.17.0     	Podinfo Helm chart for Kubernetes

    Two versions: the chart version (the package) and the app version (the software inside it). They can differ; here they happen to match.

  3. Read the knobs. Every value the chart understands is listed, with its default.

    helm show values podinfo/podinfo --version 6.17.0 | less
    Expected output (327 lines; the parts you need) 
    # Default values for podinfo.

replicaCount: 1
logLevel: info
...
image:
  repository: ghcr.io/stefanprodan/podinfo
  tag: 6.17.0
  pullPolicy: IfNotPresent
...
ui:
  color: "#34577c"
  message: ""

    Press q to leave less. Note tag: 6.17.0: a pinned version, never latest, as in session 2.

  4. Write your values file. It contains only what you change, nothing else. Copy it from examples/s3/ into your own repository.

    values-podinfo.yaml
    replicaCount: 2
ui:
  message: "installed with Helm"

  5. Render the chart on your laptop and look only at what it would create. Nothing is sent to the cluster.

    helm template demo podinfo/podinfo --version 6.17.0 -f values-podinfo.yaml | grep -E '^kind:|^# Source'
    Expected output 
    # Source: podinfo/templates/service.yaml
kind: Service
# Source: podinfo/templates/deployment.yaml
kind: Deployment
# Source: podinfo/templates/tests/grpc.yaml
kind: Pod
# Source: podinfo/templates/tests/jwt.yaml
kind: Pod
# Source: podinfo/templates/tests/service.yaml
kind: Pod

    A Service and a Deployment: the two objects from lesson 07. The three test Pods are hooks; Helm creates them only when you run helm test. Drop the | grep part to read the full YAML, and find replicas: 2 and your message in it.

  6. Rehearse the real command. --dry-run=client renders and shows what would happen, but changes nothing.[6]

    helm upgrade --install demo podinfo/podinfo --version 6.17.0 -f values-podinfo.yaml --dry-run=client
    Expected output (the first lines; the full YAML follows) 
    Release "demo" does not exist. Installing it now.
NAME: demo
LAST DEPLOYED: Thu Nov 19 10:40:47 2026
NAMESPACE: default
STATUS: pending-install
REVISION: 1
DESCRIPTION: Dry run complete
...

    Write --dry-run=client, not a bare --dry-run. Helm 4 still accepts the bare flag but prints level=WARN msg="--dry-run is deprecated and should be replaced with '--dry-run=client'". There is also --dry-run=server, which asks the API server to check the objects without storing them.

  7. Install for real. --version pins the chart, so next month you get the same thing. --wait returns only when the Pods are ready.

    helm upgrade --install demo podinfo/podinfo --version 6.17.0 -f values-podinfo.yaml --wait
    Expected output 
    Release "demo" does not exist. Installing it now.
NAME: demo
LAST DEPLOYED: Thu Nov 19 10:20:41 2026
NAMESPACE: default
STATUS: deployed
REVISION: 1
DESCRIPTION: Install complete
NOTES:
1. Get the application URL by running these commands:
  echo "Visit http://127.0.0.1:8080 to use your application"
  kubectl -n default port-forward deploy/demo-podinfo 8080:9898

    NOTES is a message from the chart's author. Charts often print the next command you need.

  8. Look with the tools you already know. Helm made ordinary objects.

    kubectl get deploy,svc,pods
    helm list
    kubectl get secret -l owner=helm
    Expected output (trimmed; your names differ) 
    deployment.apps/demo-podinfo   2/2     2            2           26s
service/demo-podinfo   ClusterIP   10.96.179.43   <none>        9898/TCP,9999/TCP   26s
pod/demo-podinfo-5fc5895c7-jmv2t   1/1     Running   0          26s
pod/demo-podinfo-5fc5895c7-qtd2v   1/1     Running   0          26s

NAME	NAMESPACE	REVISION	UPDATED                             	STATUS  	CHART         	APP VERSION
demo	default  	1       	2026-11-19 10:20:41.293351 +0100 CET	deployed	podinfo-6.17.0	6.17.0

NAME                         TYPE                 DATA   AGE
sh.helm.release.v1.demo.v1   helm.sh/release.v1   1      26s

    Two Pods, from your replicaCount: 2. One Secret: revision 1 of release demo. If your hello app from session 1 still runs, it shows up too; Helm does not touch it.

  9. Call the app. Start the tunnel in one terminal:

    kubectl port-forward deploy/demo-podinfo 9898:9898

    In a second terminal:

    curl localhost:9898
    Expected output (trimmed) 
    {
  "hostname": "demo-podinfo-5fc5895c7-jmv2t",
  "version": "6.17.0",
  ...
  "message": "installed with Helm",

    Your message, from your values file. Stop the port-forward with Ctrl+C.

  10. Change something. Edit values-podinfo.yaml to say replicaCount: 3, then run the same command as in step 7.

    helm upgrade --install demo podinfo/podinfo --version 6.17.0 -f values-podinfo.yaml --wait
    kubectl get deploy demo-podinfo
    Expected output (trimmed) 
    Release "demo" has been upgraded. Happy Helming!
NAME: demo
...
REVISION: 2
...
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
demo-podinfo   3/3     3            3           ...

  11. Read the history, roll back to revision 1, and read the history again.

    helm history demo
    helm rollback demo 1 --wait
    helm history demo
    Expected output (your times differ) 
    REVISION	UPDATED                 	STATUS    	CHART         	APP VERSION	DESCRIPTION
1       	Thu Nov 19 10:20:41 2026	superseded	podinfo-6.17.0	6.17.0     	Install complete
2       	Thu Nov 19 10:21:07 2026	deployed  	podinfo-6.17.0	6.17.0     	Upgrade complete

Rollback was a success! Happy Helming!

REVISION	UPDATED                 	STATUS    	CHART         	APP VERSION	DESCRIPTION
1       	...                     	superseded	podinfo-6.17.0	6.17.0     	Install complete
2       	...                     	superseded	podinfo-6.17.0	6.17.0     	Upgrade complete
3       	...                     	deployed  	podinfo-6.17.0	6.17.0     	Rollback to 1

    Read the last table carefully. The rollback did not delete revision 2. It created revision 3, with the content of revision 1. History only grows, so you can always see what happened.[5]

  12. Check the cluster agrees, and look at what Helm stored.

    kubectl get deploy demo-podinfo
    kubectl get secret -l owner=helm
    helm get values demo
    Expected output (trimmed) 
    NAME           READY   UP-TO-DATE   AVAILABLE   AGE
demo-podinfo   2/2     2            2           ...

NAME                         TYPE                 DATA   AGE
sh.helm.release.v1.demo.v1   helm.sh/release.v1   1      ...
sh.helm.release.v1.demo.v2   helm.sh/release.v1   1      ...
sh.helm.release.v1.demo.v3   helm.sh/release.v1   1      ...

USER-SUPPLIED VALUES:
replicaCount: 2
ui:
  message: installed with Helm

    Back to two Pods. Three revisions, three Secrets. helm get values reads the current revision's Secret and shows the values that are live now: 2, although your file still says 3. That is drift between the file and the cluster, exactly like kubectl rollout undo in lesson 07. In real work a rollback is the emergency brake; the lasting fix goes back into the file.

  13. Remove everything the release created, in one command.

    helm uninstall demo
    kubectl get secret -l owner=helm
    Expected output 
    release "demo" uninstalled
No resources found in default namespace.

    The Deployment, the Service, the Pods and the history Secrets are gone. Set replicaCount in your file back to the value you want, and commit values-podinfo.yaml. In the session you install podinfo again with this file.
