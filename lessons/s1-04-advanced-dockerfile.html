Advanced Dockerfile: multi-stage, EXPOSE, VOLUME, USER

Your win: a 20 MB image of your own web server that documents its port, declares where its data lives, and runs as a non-root user. You can explain what each of those four instructions does and what it does not do.

Before this: you have a Go server with / and /healthz that reads its port from PORT, the hello:single image from lesson 03, and Docker running (Docker Desktop on a Mac, Docker Engine on Linux or WSL).

Multi-stage: build fat, ship thin

An image is a stack of read-only layers: each instruction in a Dockerfile adds one.[1] Everything a layer adds stays in the image for good, including the whole Go toolchain you only needed for one minute to compile.

A multi-stage build fixes this. The first stage has the compiler and builds the binary. The second stage starts from an almost empty base and copies only what you name across with COPY --from. Nothing else from the first stage reaches the final image.[2]

Go makes this dramatic: with CGO_ENABLED=0 the binary is static, so the run stage needs no OS libraries at all. Google's distroless static image is about 2 MB and has no shell and no package manager.[3]

EXPOSE: a label, not a door

EXPOSE 8080 records in the image that the app listens on port 8080. It does not open or publish anything.[4] The port only becomes reachable from your laptop when you publish it at run time: -p 8080:8080 picks the host port, -P publishes every exposed port on a random free host port. And it does not tell your server which port to use: that is still PORT.

VOLUME: data that outlives the container

A container's writable layer is deleted with the container. A volume is storage managed by Docker that lives outside it, so the data survives docker rm and can be mounted into the next container.[5] VOLUME /data marks /data as such a place: if you start the container without mounting anything there, Docker creates an anonymous volume for it.[6]

A fresh named volume is filled from the image the first time it is mounted, ownership included. So the directory must already belong to the user that will write to it. Otherwise that user gets Permission denied.

Your server writes nothing to disk, and in the homework the state lives in Redis. That is on purpose: twelve-factor processes are stateless. VOLUME is here so you can read it in other people's images (every database image has one). Kubernetes ignores VOLUME: there, a Pod gets storage only when its spec asks for it.

USER: who the process is

Without USER, the process runs as root inside the container. USER sets the user (and optionally the group) for RUN steps that follow and for the running container.[7] If your server has an exploitable bug, the attacker then holds an unprivileged user, not root.[8]

Write the user as a number: USER 65532:65532 (distroless calls this user nonroot). Kubernetes can enforce "never run as root" with runAsNonRoot, but it can only check a numeric user. With a name, the Pod stays in CreateContainerConfigError and its events say: container has runAsNonRoot and image has non-numeric user (nonroot), cannot verify user is non-root.[9]

Do it

  1. Check that the naive image from lesson 03 is still there:

    docker images hello:single

    If it is missing, rebuild it from your Dockerfile.single:

    docker build -f Dockerfile.single -t hello:single .

  2. Now the real one. Read every line before you save it, and use the comments to check that you know why each line is there.

    Dockerfile

    # Stage 1: build: has the Go toolchain
FROM golang:1.27 AS build
WORKDIR /src
# go.mod changes rarely → this layer stays cached
COPY go.mod ./
# your code changes often → only this step and below rebuild
COPY *.go ./
RUN CGO_ENABLED=0 go build -o /server .
# an empty directory for the volume (distroless has no mkdir)
RUN mkdir /data

# Stage 2: run: only what we copy across
FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /server /server
# the volume directory must belong to the user that writes to it
COPY --from=build --chown=65532:65532 /data /data
VOLUME /data
# documentation: the server listens here (unless PORT says otherwise)
EXPOSE 8080
# numeric, so Kubernetes can verify it is not root
USER 65532:65532
ENTRYPOINT ["/server"]

    Add a .dockerignore so the build context stays small:[10]

    .dockerignore

    .git
*.md
Dockerfile*
    docker build -t hello:multi .

  3. Multi-stage. Compare the two images.

    docker images hello
    Expected output (sizes vary by Docker version) 
    REPOSITORY   TAG      ...   SIZE
hello        multi    ...   19.1MB
hello        single   ...   1.43GB

    All three new instructions are recorded in the image's config:

    docker inspect hello:multi --format '{{.Config.User}} {{json .Config.ExposedPorts}} {{json .Config.Volumes}}'
    Expected output 
    65532:65532 {"8080/tcp":{}} {"/data":{}}

  4. EXPOSE. Run with -P and let Docker publish the exposed port on a random host port. Ask Docker which one it picked, then call it (use your port number).

    docker run -d --name hello -P hello:multi
    docker port hello
    curl localhost:55000/healthz
    Expected output (your port differs) 
    8080/tcp -> 0.0.0.0:55000
ok

  5. USER. Look at the running process from outside, then try to get a shell inside.

    docker top hello -o user,pid,cmd
    docker exec -it hello sh
    Expected output 
    USER    PID     CMD
65532   154698  /server
OCI runtime exec failed: exec failed: unable to start container process:
exec: "sh": executable file not found in $PATH: unknown

    That error is the point: there is no shell to exec into. When you need to debug a distroless container, you attach a debug container instead; you will meet kubectl debug later.

  6. VOLUME. You started the container without mounting anything, so Docker created an anonymous volume for /data:

    docker inspect hello --format '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{end}}'
    Expected output (the long name is random) 
    volume e7607f92f35e…bb0478d85 -> /data

    Remove the container and its anonymous volume (-v), then start again with a named volume:

    docker rm -f -v hello
    docker run -d --name hello -p 8080:8080 -v hello-data:/data hello:multi

    Your server writes nothing, so write a file into the volume with a tiny busybox container running as the same user, 65532:

    docker run --rm --user 65532 -v hello-data:/data busybox:1.37 sh -c 'echo "written at $(date -u +%H:%M)" > /data/note.txt'

    Delete the hello container. Then look into the volume:

    docker rm -f hello
    docker run --rm -v hello-data:/data busybox:1.37 ls -ln /data
    docker run --rm -v hello-data:/data busybox:1.37 cat /data/note.txt
    Expected output 
    total 4
-rw-r--r--    1 65532    0     17 Oct  6 09:03 note.txt
written at 09:03

    The container is gone; the data is not. Try it without --chown=65532:65532 in the Dockerfile, and the same write fails with sh: can't create /data/note.txt: Permission denied, because /data then belongs to root.

  7. Clean up. A named volume is never deleted for you; you have to remove it by name.

    docker volume rm hello-data
