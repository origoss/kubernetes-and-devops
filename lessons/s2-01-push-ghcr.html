Session 2 · CI/CD · about 10 minutes · after the session

Put your image where anyone can pull it

Your win: your image lives in your own registry on GitHub, and anyone, your Kubernetes cluster included, can pull it with one command.

Before this: session 1. You built hello:multi in lesson 04 and loaded it into kind as hello:0.1.0 in lesson 06, and you have a GitHub account with your course repo in it.

What a registry is

In lesson 01 you met the registry: a server that stores images and hands them out. So far hello:multi exists only on your laptop. Nobody else can run it, and neither can a cluster, unless you copy it in by hand with kind load as in session 1. A push copies it to a registry; a pull copies it back down, onto any machine.

GitHub runs one, the GitHub Container Registry at ghcr.io. It comes with the GitHub account you already have, and each image you push shows up as a package on your profile.[1]

Reading an image name

An image name is an address. Each part tells Docker where to look:[2]

ghcr.io  /  <you>  /  hello  :  0.1.0
───────     ─────     ─────     ─────
registry    namespace repository tag
(GitHub)    (your     (the      (which
            user)     image)    version)

Leave out the registry and Docker assumes Docker Hub. That is why python:3.13-slim worked in lesson 01. Leave out the tag and Docker assumes latest. The namespace must be lowercase, even if your GitHub username is not.

Why 0.1.0 and never latest

You met this trap in lesson 06. With a registry it matters even more. latest is not "the newest". It is just the tag Docker picks when you give none, and it points wherever the last push put it. Kubernetes treats it specially: for an image tagged :latest (or untagged) the default pull policy is Always, so every container start goes back to the registry. For any other tag the default is IfNotPresent.[3] In kind this bites hard: an image you loaded by hand gets ignored and re-pulled, which fails if it was never pushed. kind's own docs say: don't use a :latest tag.[4]

A version tag like 0.1.0 tells you what is running. It is still a name, though: you could push different content under it tomorrow. The only name that can never move is the digest, sha256:…, a hash of the content itself.[3]

A token, handled like a password

To push, Docker must prove it is you. GHCR accepts only a personal access token (classic); the newer fine-grained tokens do not work here. The scope write:packages is enough to push and pull.[1] GitHub's advice is blunt: treat the token like a password.[5]

So never type it into a command. Your shell saves every command line in a history file, in plain text, and anyone who reads that file later has your token. docker login --password-stdin reads the secret from standard input instead, which "prevents the password from ending up in the shell's history".[6] Below you paste the token into read -s, which keeps it in a variable without echoing it or recording it.

Do it

  1. Put your GitHub username in a variable, in lowercase. Every command below uses it.

    GH_USER=your-github-username

    A new terminal forgets the variable. Run this line again if $GH_USER comes out empty.

  2. Give your image its full address. docker tag adds a second name; nothing is copied and nothing leaves your laptop.

    docker tag hello:multi ghcr.io/$GH_USER/hello:0.1.0
    docker images | grep hello
    Expected output (your ID and times differ) 
    hello                 0.1.0    3025392c4a53   10 hours ago   19.1MB
hello                 multi    3025392c4a53   10 hours ago   19.1MB
ghcr.io/<you>/hello   0.1.0    3025392c4a53   10 hours ago   19.1MB

    Same IMAGE ID on every line: one image, three names. hello:0.1.0 is the one you made for kind in session 1.

  3. Create the token on GitHub:[5]

    • Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic).
    • Note: ghcr push from laptop. Expiration: 30 days is plenty.
    • Scopes: tick only write:packages. Leave repo and everything else unticked.
    • Click Generate token and copy it. GitHub shows it only once.

  4. Log in. The first command waits silently: paste the token and press Enter. Nothing appears, which is correct.

    read -s CR_PAT
    echo $CR_PAT | docker login ghcr.io -u $GH_USER --password-stdin
    unset CR_PAT
    Expected output 
    Login Succeeded

    GitHub's own page shows export CR_PAT=YOUR_TOKEN. That line puts the token in your history file, which is exactly what you are avoiding. read -s does the same job without that leak.

  5. Push.

    docker push ghcr.io/$GH_USER/hello:0.1.0
    Example of the shape (not real output: your layer IDs, digest and size differ) 
    The push refers to repository [ghcr.io/<you>/hello]
<layer-id>: Pushed
<layer-id>: Pushed
...
0.1.0: digest: sha256:<64 hex characters> size: <bytes>

    That sha256: line is the digest: the one name for this exact content that can never move.

  6. Make the package public. A new package is private by default, visible only to you.[7] Your cluster has no GitHub login, so it could not pull a private one.

    • Open your profile on GitHub, go to the Packages tab and click hello.
    • Click Package settings (the gear icon).
    • Under Danger Zone, click Change visibility and select Public.
    • Type hello to confirm, then click I understand the consequences, change package visibility.

    This is one-way: once a package is public, you cannot make it private again.[7] That is fine for this course; your code is public anyway.

  7. Prove it. Log out, so Docker pulls as a stranger would. Remove your local copy of the name, then pull it back from GitHub.

    docker logout ghcr.io
    docker rmi ghcr.io/$GH_USER/hello:0.1.0
    docker pull ghcr.io/$GH_USER/hello:0.1.0
    Expected output (digest shortened) 
    Removing login credentials for ghcr.io
Untagged: ghcr.io/<you>/hello:0.1.0
0.1.0: Pulling from <you>/hello
Digest: sha256:…
Status: Downloaded newer image for ghcr.io/<you>/hello:0.1.0
ghcr.io/<you>/hello:0.1.0

    rmi only says Untagged: hello:multi still names the same image, so the layers stay on disk. The pull still goes to GHCR, and it succeeds without a login. Anyone can now run your server.

    Got error from registry: denied? The package is still private, or the name has a typo. GHCR gives the same answer for both, so check the spelling first.

  8. Optional: link the package to your repository, so its GitHub page shows your README and source. Add one line to the run stage of your Dockerfile, right after its FROM:[1]

    LABEL org.opencontainers.image.source=https://github.com/<you>/<your-repo>

    Then rebuild hello:multi, tag it again and push again. The label is a new layer of metadata, so the image gets a new ID. You can also link the package by hand on its settings page.
