How much may your server use?

Your win: your Deployment declares requests and limits, and you have seen with your own eyes what happens when they are set wrong.

Before this: lesson 08, so k8s/deployment.yaml is applied and committed, and you can read Events bottom-up (lesson 06).

Two numbers, two different jobs

For each container you can set two amounts of CPU and memory:[1]

  • requests are used before the Pod runs. The scheduler places a Pod only on a node that still has that much unreserved capacity. A request is a reservation. It is not a cap: the container may use more if the node has it spare.
  • limits are enforced while the container runs, by the Linux kernel's cgroups, which you met in lesson 01. Go over the memory limit and the kernel kills the process (OOM, "out of memory"). Go over a CPU limit and the process is only slowed down, never killed.

A request can never be larger than its limit. The API refuses such a Pod.

Units

  • Memory is in bytes, usually written with a suffix. Mi is a mebibyte (1024 × 1024 bytes) and Gi a gibibyte. Mind the case: M means a million bytes, and a lowercase m on memory means thousandths of a byte, which is never what you want.[1]
  • CPU is in cores, and m means millicores. 50m is one twentieth of a core, and 1 is a whole core.

Your Go server idles at about 1.5 MB of memory and almost no CPU, so small values are honest values. We set a CPU request but no CPU limit: going over a CPU limit would only slow the server down, and the request already keeps the scheduler honest.

Do it

  1. Add a resources block to the container in k8s/deployment.yaml, at the same depth as ports.

    k8s/deployment.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: hello:0.1.1
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 16Mi
            limits:
              memory: 62Mi
    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    Expected output (trimmed) 
    deployment.apps/hello configured
service/hello unchanged
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 1 old replicas are pending termination...
deployment "hello" successfully rolled out

    Changing the Pod template made the Deployment replace every Pod, a few at a time. That is a rolling update.

  2. Check what the new Pods received. Use one of your Pod names.

    kubectl describe pod hello-8677475c9f-7kx8q
    Expected output (trimmed) 
        Limits:
      memory:  62Mi
    Requests:
      cpu:        50m
      memory:     16Mi

    The server runs fine within 62 Mi. Check with kubectl get pods and port-forward if you like.

  3. Now break it on purpose: a memory limit far too small. Set both memory values to 2Mi. Both, because a request larger than its limit is refused. Try it with only the limit changed and you get:

    The Deployment "hello" is invalid: spec.template.spec.containers[0].resources.requests: Invalid value: "16Mi": must be less than or equal to memory limit of 2Mi

    With both at 2Mi, apply and watch:

    kubectl apply -f k8s/
    kubectl get pods -w
    Expected output (after about 20 seconds; stop with Ctrl+C) 
    NAME                     READY   STATUS              RESTARTS      AGE
hello-5b6b65946-c24cf    0/1     ContainerCreating   0             0s
hello-8677475c9f-7kx8q   1/1     Running             0             7s
hello-8677475c9f-bbgwd   1/1     Running             0             7s
hello-8677475c9f-hs4fs   1/1     Running             0             6s
hello-5b6b65946-c24cf    0/1     RunContainerError   0             1s
hello-5b6b65946-c24cf    0/1     RunContainerError   1 (1s ago)    2s
hello-5b6b65946-c24cf    0/1     CrashLoopBackOff    1 (16s ago)   17s
hello-5b6b65946-c24cf    0/1     RunContainerError   2 (0s ago)    17s

    Two things to notice. The new Pod flips between RunContainerError and CrashLoopBackOff, with restarts climbing. And your three old Pods are still running: the rolling update waits for each new Pod to become ready, and this one never does. kubectl get deploy hello shows READY 3/3 but UP-TO-DATE 1. Your server is still up, running the old settings.

  4. Find the cause with describe on the failing Pod.

    kubectl describe pod hello-5b6b65946-c24cf
    Expected output (trimmed) 
        State:          Waiting
      Reason:       RunContainerError
    Last State:     Terminated
      Reason:       StartError
      Message:      failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: container init was OOM-killed (memory limit too low?)
      Exit Code:    128
...
Events:
  Type     Reason     Age                From     Message
  ----     ------     ----               ----     -------
  Normal   Created    11s (x4 over 1m)   kubelet  spec.containers{hello}: Container created
  Warning  Failed     11s (x4 over 1m)   kubelet  spec.containers{hello}: Error: failed to create containerd task: ... container init was OOM-killed (memory limit too low?)
  Warning  BackOff    11s (x3 over 1m)   kubelet  spec.containers{hello}: Back-off restarting failed container hello in pod ...

    "container init was OOM-killed (memory limit too low?)": the kernel killed the process before your server even started, because 2 Mi is not enough to start any process at all. kubectl logs has nothing to show here, because your program never ran.

    A server that starts fine and then grows past its limit fails differently: the Last State says Reason: OOMKilled with Exit Code: 137, and it ends in CrashLoopBackOff too.[1]

  5. Break it the other way: ask for far more than your laptop has. Set both memory values to 100Gi, then apply and look.

    kubectl apply -f k8s/
    kubectl get pods
    Expected output 
    NAME                     READY   STATUS    RESTARTS   AGE
hello-8677475c9f-7kx8q   1/1     Running   0          58s
hello-8677475c9f-bbgwd   1/1     Running   0          58s
hello-8677475c9f-hs4fs   1/1     Running   0          57s
hello-86c79c5c6-fg6rc    0/1     Pending   0          6s
    kubectl describe pod hello-86c79c5c6-fg6rc
    Expected output (only the Events) 
    Events:
  Type     Reason            Age              From               Message
  ----     ------            ----             ----               -------
  Warning  FailedScheduling  5s (x2 over 6s)  default-scheduler  0/1 nodes are available: 1 Insufficient memory. preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.

    This time the container never got near a kernel. The scheduler found no node with 100 Gi unreserved, so the Pod waits in Pending. It stays there until you lower the request or a big enough node joins. Note who reported it: default-scheduler, not kubelet. Requests are the scheduler's business.

    One more face of the same mistake, for the record. A ridiculously small limit such as 1Ki does not produce an OOM kill at all. The Pod hangs in ContainerCreating, and its Events repeat FailedMount ... no space left on device. Kubernetes mounts a small in-memory volume into every Pod, and that volume is sized by the memory limit, so with 1 KiB there is no room for even that. Same root cause, a misleading symptom: always check the resources when a message makes no sense.

  6. Restore the working values: requests cpu: 50m and memory: 16Mi, limit memory: 62Mi. Then apply and confirm.

    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    kubectl get pods
    Expected output 
    deployment.apps/hello configured
service/hello unchanged
deployment "hello" successfully rolled out
NAME                     READY   STATUS    RESTARTS   AGE
hello-8677475c9f-7kx8q   1/1     Running   0          58s
hello-8677475c9f-bbgwd   1/1     Running   0          58s
hello-8677475c9f-hs4fs   1/1     Running   0          57s

    The broken Pod is gone, and the three good Pods kept running the whole time. The template matches the good one again, so the Deployment simply keeps them.

  7. Run git diff. It should show only the new resources block. Then commit and push.

    git add k8s/deployment.yaml
    git commit -m "Set resource requests and limits"
    git push

You have now seen three different faces of one kind of mistake: CrashLoopBackOff with a StartError, Pending with FailedScheduling, and a ContainerCreating that never ends. Remember them. A misbehaving cluster rarely tells you which number is wrong; you have to read your way there.
