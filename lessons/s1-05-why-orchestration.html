Why orchestration?

Your win: a real Kubernetes cluster is running on your laptop, and you can say in one sentence what an orchestrator is for.

Before this: Docker, kind and kubectl work (the pre-flight check).

Pains you have already met

Plain Docker runs one container on one machine, exactly when you tell it to. That is enough on a laptop. It stops being enough the moment real users depend on your server:

  • It died, and nobody restarted it. A container that crashes at 3 a.m. stays down until a human notices.
  • I want three copies. One copy means one crash takes the service offline. Three copies means three docker run commands, three names, three ports, and you keeping count.
  • The config is baked in. A different port or setting per environment means a different command line, typed correctly every time.
  • Which machine runs it? With five servers, someone has to pick one with free memory, and pick again when it fails.

You will see the first pain for real in step 1 below. By default Docker does not restart a container at all; its default restart policy is no.[1]

What an orchestrator does

An orchestrator turns the question around. You stop giving orders ("start this container") and instead declare the state you want: "three copies of hello:0.1.0, each with 128 MB, reachable on port 80". Kubernetes stores that as an object, a "record of intent". From then on the system "will constantly work to ensure that the object exists".[2]

The workers that do this are controllers. Think of a thermostat: you set the temperature you want, it measures the temperature you have, and it switches the heating on or off to close the gap. A Kubernetes controller is the same loop. It watches the cluster, compares current state with desired state, and acts.[3] A copy crashed? Current state is two, desired is three, so it starts one. No human involved.

So, in one sentence: an orchestrator keeps the actual state of your containers matching the state you declared, across many machines.

Inside a Kubernetes cluster

A cluster is a set of machines called nodes. The control plane makes the decisions and keeps the record. The worker nodes run your containers.[4]

The control plane:[5]

  • kube-apiserver: the front door. Everything talks to it: kubectl, the controllers, the nodes. Nothing talks to the others directly.
  • etcd: the database. It holds every object, so it holds both the state you declared and the state the nodes report.
  • kube-scheduler: picks a node for each new Pod, one with enough free CPU and memory.
  • kube-controller-manager: runs the controllers from above. One of them keeps your three copies at three.

Every node:

  • kubelet: the node's agent. It asks the apiserver which Pods belong to its node, has them started, checks them (your /healthz from lesson 02) and reports back.
  • container runtime: containerd. It pulls images and runs the containers.
  • kube-proxy: sets up the network rules that let one stable Service address reach whichever Pods are behind it (lesson 07).

Follow one change through it. You ask for three copies of your server. The apiserver stores that in etcd. A controller sees zero Pods where three are wanted and creates three. The scheduler gives each one a node. The kubelet on that node has containerd start the container and reports Running. You typed one command; five components did the rest.

kind: Kubernetes nodes as containers

A real cluster spans several machines, called nodes. You have one laptop. kind solves this neatly: it "runs a local Kubernetes cluster by using Docker containers as 'nodes'".[6] Each node is a container that holds a whole Kubernetes machine inside it. A default kind cluster has a single node that is control plane and worker at once.

Remember the OCI standard from lesson 01? Here it pays off. Inside the node there is no Docker at all. Kubernetes runs its containers with containerd, and your Docker-built image will run there unchanged, because both speak the same image format.

Do it

  1. Feel the first pain. Start a container that keeps running (it just sleeps for ten minutes), check it, then kill it the way a crash would.

    docker run -d --name hello python:3.13-slim sleep 600
    docker ps --filter name=hello
    docker kill hello
    docker ps -a --filter name=hello
    Expected output (IDs and times differ) 
    CONTAINER ID   IMAGE              COMMAND       CREATED         STATUS         PORTS     NAMES
6f7434adc543   python:3.13-slim   "sleep 600"   2 seconds ago   Up 2 seconds             hello
hello
CONTAINER ID   IMAGE              COMMAND       CREATED          STATUS                       PORTS     NAMES
6f7434adc543   python:3.13-slim   "sleep 600"   10 seconds ago   Exited (137) 3 seconds ago             hello

    Exit code 137 means "killed". It stays dead: no restart, no warning. Wait a minute and check again; nothing changes. Clean up:

    docker rm hello

  2. Create a Kubernetes cluster. You pulled its node image in the pre-flight check, so this takes about a minute.

    kind create cluster
    Expected output (the version and the last line vary) 
    Creating cluster "kind" ...
 ✓ Ensuring node image (kindest/node:v1.37.0) 🖼
 ✓ Preparing nodes 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing CNI 🔌
 ✓ Installing StorageClass 💾
Set kubectl context to "kind-kind"
You can now use your cluster with:

kubectl cluster-info --context kind-kind

Have a question, bug, or feature request? Let us know! https://kind.sigs.k8s.io/#community 🙂

  3. Ask the cluster who it is, and which nodes it has.

    kubectl cluster-info
    kubectl get nodes
    Expected output (your port differs) 
    Kubernetes control plane is running at https://127.0.0.1:62635
CoreDNS is running at https://127.0.0.1:62635/api/v1/namespaces/kube-system/services/kube-dns:dns/proxy

To further debug and diagnose cluster problems, use 'kubectl cluster-info dump'.

NAME                 STATUS   ROLES           AGE   VERSION
kind-control-plane   Ready    control-plane   29s   v1.37.0

    One node. If it says NotReady, wait 20 seconds and ask again: the node network is still starting.

  4. How did kubectl know where your cluster is? From its kubeconfig file, ~/.kube/config. kind wrote into it when it created the cluster.[6] The file holds three lists:[7]

    • clusters: where an API server is, with its address and certificate;
    • users: how you prove who you are, here with a client certificate;
    • contexts: a named pair of one cluster and one user.

    The current context decides which cluster every kubectl command goes to. kind named its context kind-kind.

    kubectl config get-contexts
    kubectl config view --minify
    Expected output (your port differs) 
    CURRENT   NAME        CLUSTER     AUTHINFO    NAMESPACE
*         kind-kind   kind-kind   kind-kind

apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: DATA+OMITTED
    server: https://127.0.0.1:62635
  name: kind-kind
contexts:
- context:
    cluster: kind-kind
    user: kind-kind
  name: kind-kind
current-context: kind-kind
kind: Config
users:
- name: kind-kind
  user:
    client-certificate-data: DATA+OMITTED
    client-key-data: DATA+OMITTED

    The * marks the current context. --minify shows only the parts the current context uses, and hides the keys as DATA+OMITTED. The server line is the port Docker forwards, the same address kubectl cluster-info printed.

    The real file contains the admin key to your cluster. Never commit it to Git or paste it anywhere.

    More than one context listed, for example docker-desktop from an earlier install? Switch with kubectl config use-context kind-kind. To point kubectl at a different file instead of ~/.kube/config, set the KUBECONFIG environment variable.

    Seeing The connection to the server localhost:8080 was refused? kubectl found no current context and fell back to localhost:8080, where nothing listens. While the cluster runs, kind export kubeconfig writes the context back.

  5. Now look at the same thing from Docker's side.

    docker ps
    Expected output (other containers of yours may be listed too) 
    CONTAINER ID   IMAGE                  COMMAND                  CREATED         STATUS         PORTS                       NAMES
5c45788fed2b   kindest/node:v1.37.0   "/usr/local/bin/entr…"   33 seconds ago  Up 31 seconds  127.0.0.1:62635->6443/tcp   kind-control-plane

    Your whole cluster is this one container. Its port is the address kubectl cluster-info printed.

  6. Look inside the node. crictl is the tool for talking to containerd there.

    docker exec kind-control-plane crictl ps
    Expected output (trimmed: some columns dropped) 
    CONTAINER       IMAGE           ...   STATE     NAME                      ...   NAMESPACE
22751856e7b83   fbccbf70a429f   ...   Running   coredns                   ...   kube-system
84f241463e163   fbccbf70a429f   ...   Running   coredns                   ...   kube-system
a0018e2a16939   0771a8a05619f   ...   Running   local-path-provisioner    ...   local-path-storage
ca74a69638958   550b682d81d41   ...   Running   kube-proxy                ...   kube-system
89834beb78d11   8e13ccc0aaa68   ...   Running   kindnet-cni               ...   kube-system
2a4a3c69d71a9   c2e426bbd1cd6   ...   Running   etcd                      ...   kube-system
eab45a23ad04f   b1ad0e33c9012   ...   Running   kube-controller-manager   ...   kube-system
1b4a168c5cfa9   384eabc4fe526   ...   Running   kube-scheduler            ...   kube-system

    The control plane from the diagram runs as containers: kube-apiserver, etcd, kube-scheduler, kube-controller-manager, plus kube-proxy. The kubelet is missing because it is not a container: it is an ordinary service on the node that starts all the others. In the next lessons your app joins this list, run by containerd, not Docker.

  7. Leave the cluster running. Lesson 06 starts from it.

    After a laptop reboot: kind gives its node container a restart policy, so when Docker starts again the node usually comes back with your cluster in it. Check with docker inspect kind-control-plane --format '{{.HostConfig.RestartPolicy.Name}}', which prints on-failure. If kubectl get nodes errors after a reboot, start over; it takes a minute. When you are finished with it for good, kind delete cluster removes it, and its context from your kubeconfig.[6]
