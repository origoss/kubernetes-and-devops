Four verbs to find out what is wrong

Your win: you can find out why anything in a cluster is unhappy, using four verbs: get, describe, logs and events.

Before this: your kind cluster from lesson 05 is running, and kubectl get nodes shows kind-control-plane as Ready. You have the hello:multi image from lesson 04.

Nobody shows you an error dialog

In Kubernetes you declare what you want, and controllers keep trying to make it true. When something goes wrong, nothing pops up and nothing crashes in your terminal. The cluster just keeps trying, and it writes down what it tried. Your job is to read that record.

Four verbs cover almost every case. Each one answers a different question:[1]

  • kubectl get: What exists, and what state is it in? Add -A for all namespaces, -o wide for extra columns such as the node and the IP, and -w to keep watching for changes.[2]
  • kubectl describe: What does the cluster know about this one object, and what happened to it? It ends with the object's Events.[3]
  • kubectl logs: What did my program print? Add --previous to see the run before the last restart.[4]
  • kubectl events: What happened recently? Add --for pod/NAME to see one object's story.[5]

The order matters. Start with get to find the unhappy object. Then describe it. Reach for logs only once a container has actually started: a container that never ran has nothing to print.

Read the Events bottom-up

If you learn one skill today, make it this one. The Events table at the end of describe lists the oldest event at the top and the newest at the bottom. So read it from the bottom:

  1. The last line says what is going on now, for example "back-off".
  2. Walk up to the first Warning with a real message. That line usually names the cause.
  3. (x4 over 2m) means the same event happened four times. Repetition means "still broken, still retrying".

Events are short-lived: the cluster deletes old ones after a while. On a pod that has been healthy for hours, Events: <none> is normal, not a bug.

Do it

  1. Look at everything running in the cluster, in all namespaces.

    kubectl get pods -A
    Expected output (name suffixes and ages differ) 
    NAMESPACE            NAME                                         READY   STATUS    RESTARTS   AGE
kube-system          coredns-559f6c778d-bgl74                     1/1     Running   0          12s
kube-system          coredns-559f6c778d-psxpm                     1/1     Running   0          12s
kube-system          etcd-kind-control-plane                      1/1     Running   0          21s
kube-system          kindnet-zg95x                                1/1     Running   0          13s
kube-system          kube-apiserver-kind-control-plane            1/1     Running   0          21s
kube-system          kube-controller-manager-kind-control-plane   1/1     Running   0          20s
kube-system          kube-proxy-pd9vv                             1/1     Running   0          13s
kube-system          kube-scheduler-kind-control-plane            1/1     Running   0          20s
local-path-storage   local-path-provisioner-75f7fc7dc5-vt5pj      1/1     Running   0          12s

    Without -A you only see the default namespace, which is empty so far. Try kubectl get pods and you get No resources found in default namespace.

    READY 1/1 means one of one containers is ready. RESTARTS counts how often a container has died and been started again. A climbing number there is always worth a look.

  2. Get more columns for one namespace.

    kubectl get pods -n kube-system -o wide
    Expected output (trimmed) 
    NAME                       READY   STATUS    RESTARTS   AGE   IP           NODE                 ...
coredns-559f6c778d-bgl74   1/1     Running   0          13s   10.244.0.2   kind-control-plane   ...
coredns-559f6c778d-psxpm   1/1     Running   0          13s   10.244.0.4   kind-control-plane   ...
etcd-kind-control-plane    1/1     Running   0          22s   172.18.0.3   kind-control-plane   ...

    Now you can see which node each pod runs on and its IP. With one node the answer is always the same, but on a real cluster this is how you spot "everything broken lives on node 3".

  3. Describe one of the CoreDNS pods, the cluster's internal DNS server. Copy a name from your own output (Tab completion works if you set it up).

    kubectl describe pod -n kube-system coredns-559f6c778d-bgl74
    Expected output (trimmed to the parts that matter today) 
    Name:                 coredns-559f6c778d-bgl74
Namespace:            kube-system
Node:                 kind-control-plane/172.18.0.3
Status:               Running
Controlled By:  ReplicaSet/coredns-559f6c778d
Containers:
  coredns:
    Image:         registry.k8s.io/coredns/coredns:v1.14.6
    State:          Running
    Ready:          True
    Restart Count:  0
...
Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  20s   default-scheduler  0/1 nodes are available: 1 node(s) had untolerated taint(s). ...
  Normal   Scheduled         10s   default-scheduler  Successfully assigned kube-system/coredns-559f6c778d-bgl74 to kind-control-plane
  Normal   Pulled            9s    kubelet            spec.containers{coredns}: Container image "registry.k8s.io/coredns/coredns:v1.14.6" already present on machine ...
  Normal   Created           9s    kubelet            spec.containers{coredns}: Container created
  Normal   Started           9s    kubelet            spec.containers{coredns}: Container started
  Warning  Unhealthy         9s    kubelet            spec.containers{coredns}: Readiness probe failed: Get "http://10.244.0.2:8181/ready": dial tcp 10.244.0.2:8181: connect: connection refused

    Practise reading bottom-up on a healthy pod. The two warnings are start-up noise: at first the node was not ready yet, and the readiness check ran a moment before the server listened. The pod is Running and Ready: True, so both problems went away by themselves. A warning only matters if it is still happening. If your cluster is older than an hour or so, you will probably see Events: <none> instead.

  4. Read what the CoreDNS program printed.

    kubectl logs -n kube-system coredns-559f6c778d-bgl74
    Expected output 
    maxprocs: Leaving GOMAXPROCS=12: CPU quota undefined
.:53
[INFO] plugin/reload: Running configuration SHA512 = 1b226df7...
CoreDNS-1.14.6
linux/arm64, go1.26.5, 424d125

    Logs are whatever the program writes to stdout and stderr. Kubernetes adds nothing to them.

  5. Bring your own image into the cluster. The kind node cannot see the images in your laptop's Docker: it runs its own containerd. Give your image a version tag, then copy it into the node with kind load.[6]

    docker tag hello:multi hello:0.1.0
    kind load docker-image hello:0.1.0
    docker exec kind-control-plane crictl images | grep hello
    Expected output (your IDs differ) 
    Image: "hello:0.1.0" with ID "sha256:3025392c4a53d39676a08aaa88cb753b1bbae7680f96a176787bc2cfff506610" not yet present on node "kind-control-plane", loading...
docker.io/library/hello                         0.1.0                6da0c4b727f58       5.35MB

    Inside the node your image is listed as docker.io/library/hello. A name without a registry means Docker Hub, and containerd writes the full name out.

    Why 0.1.0 and never latest? For an image tagged :latest, or with no tag at all, the default pull policy is Always: every start asks the registry, and the copy you loaded is ignored. For any other tag the default is IfNotPresent, so the loaded copy is used.[7] kind's docs warn about exactly this.[6] With hello:latest your Pod would end in ImagePullBackOff.

  6. Now break something on purpose. Start a pod from a tag you never loaded, and watch it. Press Ctrl+C to stop watching after about 20 seconds.

    kubectl run broken --image=hello:0.0.0-doesnotexist
    kubectl get pods -w
    Expected output 
    pod/broken created
NAME     READY   STATUS              RESTARTS   AGE
broken   0/1     ContainerCreating   0          0s
broken   0/1     ErrImagePull        0          1s
broken   0/1     ImagePullBackOff    0          16s

    ErrImagePull is the first failure. ImagePullBackOff means "I failed, and I am waiting longer and longer before the next try". The pod does not give up, and it does not tell you why. For that you need the next verb.

  7. Describe it, then read the Events bottom-up.

    kubectl describe pod broken
    Expected output (trimmed) 
    Name:             broken
Status:           Pending
Containers:
  broken:
    Image:          hello:0.0.0-doesnotexist
    State:          Waiting
      Reason:       ImagePullBackOff
    Ready:          False
    Restart Count:  0
...
Events:
  Type     Reason     Age               From               Message
  ----     ------     ----              ----               -------
  Normal   Scheduled  25s               default-scheduler  Successfully assigned default/broken to kind-control-plane
  Normal   BackOff    24s               kubelet            spec.containers{broken}: Back-off pulling image "hello:0.0.0-doesnotexist"
  Warning  Failed     24s               kubelet            spec.containers{broken}: Error: ImagePullBackOff
  Normal   Pulling    9s (x2 over 25s)  kubelet            spec.containers{broken}: Pulling image "hello:0.0.0-doesnotexist"
  Warning  Failed     8s (x2 over 24s)  kubelet            spec.containers{broken}: Failed to pull image "hello:0.0.0-doesnotexist": failed to pull and unpack image "docker.io/library/hello:0.0.0-doesnotexist": failed to resolve reference "docker.io/library/hello:0.0.0-doesnotexist": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
  Warning  Failed     8s (x2 over 24s)  kubelet            spec.containers{broken}: Error: ErrImagePull

    Bottom line: ErrImagePull, the symptom. One line up is the first Failed with a long message, and there is the cause. The node has no image called hello:0.0.0-doesnotexist, so containerd asked Docker Hub for docker.io/library/hello, and Docker Hub answered pull access denied, repository does not exist. Fix the tag and the pod recovers.

    You will meet this exact message again: it is what you get when you forget kind load, or use :latest. The node looks for an image that only exists on your laptop.

  8. Try the other two verbs on the same pod.

    kubectl logs broken
    kubectl events --for pod/broken
    Expected output (trimmed) 
    Error from server (BadRequest): container "broken" in pod "broken" is waiting to start: trying and failing to pull image
LAST SEEN          TYPE      REASON      OBJECT       MESSAGE
25s                Normal    Scheduled   Pod/broken   Successfully assigned default/broken to kind-control-plane
24s                Normal    BackOff     Pod/broken   Back-off pulling image "hello:0.0.0-doesnotexist"
24s                Warning   Failed      Pod/broken   Error: ImagePullBackOff
9s (x2 over 25s)   Normal    Pulling     Pod/broken   Pulling image "hello:0.0.0-doesnotexist"
8s (x2 over 24s)   Warning   Failed      Pod/broken   Failed to pull image ...: pull access denied, repository does not exist ...
8s (x2 over 24s)   Warning   Failed      Pod/broken   Error: ErrImagePull

    logs has nothing: the container never started, so your program never printed a line. events shows the same story as the bottom of describe, without the rest.

  9. Now a pod whose image is fine but whose program crashes. Your server reads its port from PORT, so give it nonsense.

    kubectl run crashy --image=hello:0.1.0 --env=PORT=notaport

    Wait half a minute, then:

    kubectl get pod crashy
    kubectl logs crashy
    Expected output (the status flips between Error and CrashLoopBackOff) 
    NAME     READY   STATUS   RESTARTS      AGE
crashy   0/1     Error    2 (34s ago)   35s
2026/10/06 08:33:52 listening on :notaport
2026/10/06 08:33:52 listen tcp: lookup tcp/notaport: unknown port

    This time logs is the verb that answers. CrashLoopBackOff means "it started, it died, I restarted it, it died again, and now I wait before the next try". The cause is in your own program's output.

  10. One more case. Sometimes a container crashes, gets restarted, and is Running again when you look. The current logs then show only the fresh start. --previous shows the run that died. This pod prints a line, waits 15 seconds and exits with an error:

    kubectl run flaky --image=busybox:1.37 -- sh -c 'echo "started at $(date +%T)"; sleep 15; echo "giving up"; exit 1'

    Wait about 20 seconds, so that it has restarted once, then compare:

    kubectl logs flaky
    kubectl logs flaky --previous
    Expected output 
    started at 22:31:34
started at 22:31:19
giving up

    The first command shows the new run, which has not failed yet. The second shows the old run, including its last words.

  11. Clean up all three.

    kubectl delete pod broken crashy flaky

Check yourself

Answer from memory first. Wrong picks explain themselves.

Predict the outputYou run a pod with an image tag that does not exist. Which STATUS values does kubectl get pods -w show, in order?
Predict the outputThe pod broken is in ImagePullBackOff. What does kubectl logs broken print?
