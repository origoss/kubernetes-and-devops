Session 3 · Observability · about 30 minutes · after the session

Logs: from a spike to the lines behind it

Your win: from an error-rate spike to the exact log lines behind it, in one Grafana window. Your hello server writes JSON logs, Alloy ships every Pod's output to Loki, and you query it with LogQL next to your Prometheus panel.

Before this: lesson 05. Your kind cluster runs kube-prometheus-stack (release kps, namespace monitoring) from your values-kps.yaml, and hello:0.2.0 runs with its ServiceMonitor and PrometheusRule from k8s/. You work in your own hello repository, where monitoring/values-kps.yaml lives since lesson 03. Run git pull in the course repository first: this lesson copies two more files from its examples/s3/.

Why logs need a system

Metrics told you that something is wrong: the error ratio went up. The why is usually in a log line. So far you read those with kubectl logs. It has three limits:

  • It dies with the Pod. The kubelet keeps the log of one previous container run, that is all. Delete or evict the Pod and its logs are gone.[1] A rollout replaces every Pod, so a rollout deletes your evidence.
  • One container at a time. kubectl logs deploy/hello picks one Pod and prints Found 2 pods, using pod/…. The other Pod's lines are not there.
  • No "yesterday". You cannot ask "show me every error from all Pods between 14:02 and 14:05".

Kubernetes says it plainly: logs need "a separate storage and lifecycle independent of nodes, pods, or containers", and Kubernetes itself does not provide that storage.[1] The usual answer is a node agent: one collector per node, run as a DaemonSet, that picks up every container's output and pushes it to a log store. In this lesson the agent is Alloy and the store is Loki.

Structured logs: one JSON object per line

Your server prints listening on :8080 and nothing else. A useful log line answers questions: which request, what status, how bad. Write it as JSON, one object per line, and a machine can filter on any field later.

Go has this built in. The log/slog package's JSONHandler "writes Records to an io.Writer as line-delimited JSON objects".[2] You set it as the default logger once, then log one line per request from the middleware you wrote in lesson 05: INFO for normal requests, ERROR when the status is 500 or above.

Write the line to stdout. The container runtime saves stdout and stderr; the node agent picks them up from there. Your program never needs to know where its logs end up.

Three parts

PartRuns asJob
LokiStatefulSet loki, one Pod, single-binary mode, logs on a filesystem volumeStores log lines and answers queries. It indexes only the labels of each stream, not the text of the lines.[3]
AlloyDaemonSet alloy: one Pod per nodeAsks the Kubernetes API which Pods run on its node, gives their logs labels (namespace, pod, container, app), tails them, pushes them to Loki.
Grafanaalready there, from kpsGets one more data source, Loki. Then Explore speaks LogQL next to PromQL.

Why "labels only" makes Loki cheap. A search engine indexes every word of every line, and that index can grow bigger than the logs. Loki does not. A stream is all lines with the same set of labels, for example {namespace="default", app="hello", pod="hello-9c5c5cb84-tmknd", container="hello"}. Loki indexes those label sets, and stores the lines themselves as compressed chunks. "A small index and highly compressed chunks simplify the operation and significantly lower the cost of Loki."[3] The price: searching for text inside lines means reading those chunks. So you always narrow down by labels first.

The pipeline

container stdout
      │  (the kubelet serves it through the Kubernetes API)
      ▼
┌───────────── Alloy Pod (DaemonSet, one per node) ──────────────┐
│ discovery.kubernetes   "which Pods run on my node?"            │
│        ▼  targets                                              │
│ discovery.relabel      "label them: namespace, pod, app, ..."  │
│        ▼  output                                               │
│ loki.source.kubernetes "tail their logs"                       │
│        ▼  forward_to                                           │
│ loki.write             "push to Loki"                          │
└────────────────────────────────────────────────────────────────┘
      │  HTTP push to loki.monitoring:3100
      ▼
Loki (StatefulSet) ──► Grafana Explore (LogQL)

Alloy's configuration is its own small language. You declare components, each with a type and a name, and wire them by name: one component reads another's export as type.name.export, for example discovery.kubernetes.pods.targets.[4] Read the config in examples/s3/values-alloy.yaml top to bottom, following the names:

examples/s3/values-alloy.yaml
# Alloy as a DaemonSet: one collector per node, shipping Pod logs to Loki.
controller:
  type: daemonset
alloy:
  resources:
    requests: { cpu: 50m, memory: 64Mi }
    limits: { memory: 256Mi }
  configMap:
    content: |
      // 1. Find the Pods on this node through the Kubernetes API.
      discovery.kubernetes "pods" {
        role = "pod"
        selectors {
          role  = "pod"
          field = "spec.nodeName=" + sys.env("HOSTNAME")
        }
      }

      // 2. Turn Kubernetes metadata into a few Loki labels.
      discovery.relabel "pods" {
        targets = discovery.kubernetes.pods.targets
        rule {
          source_labels = ["__meta_kubernetes_namespace"]
          target_label  = "namespace"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_name"]
          target_label  = "pod"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_container_name"]
          target_label  = "container"
        }
        rule {
          source_labels = ["__meta_kubernetes_pod_label_app"]
          target_label  = "app"
        }
      }

      // 3. Tail those Pods' logs.
      loki.source.kubernetes "pods" {
        targets    = discovery.relabel.pods.output
        forward_to = [loki.write.default.receiver]
      }

      // 4. Push to Loki.
      loki.write "default" {
        endpoint {
          url = "http://loki.monitoring:3100/loki/api/v1/push"
        }
      }
  1. discovery.kubernetes "pods" lists Pods from the API. The selectors block narrows the list with a field selector: only Pods whose spec.nodeName equals this Alloy Pod's HOSTNAME. The Alloy chart sets HOSTNAME to the node's name, so each Alloy takes only its own node's Pods. With three nodes, three Alloys share the work and no line is shipped twice. Grafana's docs show the same selector and say it "significantly" cuts API server load.[5]
  2. discovery.relabel "pods" takes those targets and copies four pieces of metadata into labels. The last rule copies the Pod's app label, which your hello Pods carry. A Pod without an app label simply gets no app label in Loki.
  3. loki.source.kubernetes "pods" tails the logs of those Pods "using the Kubernetes API", without reading files on the node's disk.[6] It hands every line to forward_to.
  4. loki.write "default" pushes to the Loki Service in namespace monitoring. Its receiver export is what step 3 points at.

Labels starting with __meta_ are the same discovery metadata Prometheus uses for scrape targets. Relabelling is the same idea too: copy what you need into real labels, the rest is dropped.

Loki on a laptop: single binary

Out of the box, the Loki chart installs simple scalable mode: separate read, write and backend Pods.[7] The chart's own values say that mode requires object storage, such as S3. That is the right shape for a team's production logs, and far too much for kind on a laptop.

Monolithic mode "runs all of Loki's microservice components inside a single process as a single binary".[7] Your values-loki.yaml switches to it and keeps the chunks on the Pod's own volume:

examples/s3/values-loki.yaml
# Loki in single-binary mode with filesystem storage: one Pod, no object store.
deploymentMode: SingleBinary
loki:
  auth_enabled: false
  commonConfig:
    replication_factor: 1
  storage:
    type: filesystem
  schemaConfig:
    configs:
      - from: "2024-04-01"
        store: tsdb
        object_store: filesystem
        schema: v13
        index:
          prefix: loki_index_
          period: 24h
singleBinary:
  replicas: 1
  resources:
    requests: { cpu: 100m, memory: 256Mi }
    limits: { memory: 512Mi }
# Turn off the scalable components and the extras this lesson does not need.
read: { replicas: 0 }
write: { replicas: 0 }
backend: { replicas: 0 }
gateway: { enabled: false }
chunksCache: { enabled: false }
resultsCache: { enabled: false }
lokiCanary: { enabled: false }
test: { enabled: false }

auth_enabled: false means one tenant, no login: fine inside your own cluster. The schemaConfig says how Loki lays out its index on disk; copy it as it is.

LogQL: labels first, then text

A LogQL query starts with a stream selector in braces. It is mandatory.[8] After it comes an optional pipeline of stages, each starting with |. It is the same mental model as PromQL: select by labels first, then work on what you selected. LogQL is in fact based on PromQL.[8]

QueryWhat it does
{namespace="default", app="hello"}Stream selector: every line from streams with these labels. Uses the index.
{app="hello"} |= "boom"Line filter: keep lines that contain the text, "a distributed grep".[9]
{app="hello"} | json | level="ERROR"Parser: json turns every JSON field into a label, at query time. Then filter on it.
sum by (status) (count_over_time({app="hello"} | json [5m]))Metric query: count lines per stream over 5 minutes, sum by status. Logs become numbers.[10]

Order matters for speed. Put line filters early: every later stage then runs only on the lines that survived.[9]

Cardinality bites here too. In lesson 05 you labelled metrics by route, never by raw URL. Loki has the same rule: every new combination of label values is a new stream, so labels should have few values, "ideally limited to tens", and an ID such as a request ID or trace ID must never become a label.[11] Look up one request with a line filter instead: {app="hello"} |= "the-id". The pod label is normal: it changes only when a Pod is replaced, so its values stay few. Fields that | json extracts at query time are not stored as labels, so a raw path inside the line is harmless.

  4. Stop and think: which pattern was that? You changed a values file, ran helm upgrade, and a Pod restarted or reloaded. Compare with the two ways of adding a scrape target in lesson 04. Answer before you open the box.

    Our answer

    The config-file pattern, with Helm doing the tedious part. Loki's and Alloy's settings end up in plain ConfigMaps (loki, alloy); no operator watches a custom resource for them. Helm renders the new ConfigMap and applies it. Then something has to notice: Alloy's config-reloader sidecar calls Alloy's reload endpoint, much like the /-/reload you ran by hand in lesson 04. Loki's Pod template carries a checksum/config annotation, so a changed config changes the template and the StatefulSet replaces the Pod. A typo still only shows up when the program reads its file, as in lesson 04.

    The operator style exists for logs too: the Alloy chart installed a CRD, podlogs.monitoring.grafana.com (see kubectl get crd | grep grafana), read by Alloy's loki.source.podlogs component,[12] and Grafana publishes an alloy-operator chart that manages Alloy itself from a custom resource. This course does not use either; you now know what to look for.

Query your logs

  1. In Grafana, open Explore, pick the Loki data source and switch the query editor to Code. Run each query; look at the lines and at the labels Grafana shows under a line when you click it.

    {namespace="default", app="hello"}
    Expected output (one line of many) 
    {"time":"...","level":"INFO","msg":"request","method":"GET","path":"/","status":200,"duration_ms":0}
    {app="hello"} |= "boom"
    Expected output (one line of many) 
    {"time":"...","level":"ERROR","msg":"request","method":"GET","path":"/boom","status":500,"duration_ms":0}
    {app="hello"} | json | level="ERROR"
    Expected output (the labels of one result line) 
    app=hello  container=hello  detected_level=error  duration_ms=0
instance=default/hello-9c5c5cb84-tmknd:hello  job=loki.source.kubernetes.pods
level=ERROR  method=GET  msg=request  namespace=default  path=/boom
pod=hello-9c5c5cb84-tmknd  service_name=hello  status=500  time=2026-11-19T09:38:24.559228716Z

    After | json, every JSON field is a label you can filter on: level, path, status. A few labels you did not write come from Alloy and Loki themselves: instance, job, service_name, detected_level.

    sum by (status) (count_over_time({app="hello"} | json [5m]))
    Expected output (your numbers differ) 
    {}             2
{status="200"} 186
{status="500"} 182

    Roughly half the requests fail, as the loop intends. The {} series, with no status: those are the two "msg":"listening" lines, one per Pod, which have no status field.

  2. Find a stream that is not there. Your podinfo release from lesson 01 still runs. Try:

    {app="demo-podinfo"}

    No data. podinfo's Pods are labelled app.kubernetes.io/name=demo-podinfo, not app, and your relabel rule only copies app. Select it by labels that every Pod has instead:

    {namespace="default", pod=~"demo-podinfo.*"}

    Lines appear. Lesson: when a query is empty, check which labels the stream really has before you blame Alloy. In Explore, the Label browser lists them.

From symptom to cause

  1. Your loop has been sending half of the requests to /boom for a few minutes. Look at the symptom first. In the Prometheus UI (kubectl -n monitoring port-forward svc/kps-prometheus 9090:9090), open Alerts: HelloHighErrorRate from lesson 05 is firing (it was pending for its for: 2m first). Your dashboard panel from lesson 05 shows the error ratio near 0.5.

  2. Now the cause, in one window. In Grafana Explore:

    1. Pick Prometheus and run the error ratio from lesson 05: sum(rate(http_requests_total{job="hello", status=~"5.."}[1m])) / sum(rate(http_requests_total{job="hello"}[1m])).
    2. Click Split. A second pane opens next to the first.
    3. In the right pane, pick Loki and run {app="hello"} | json | level="ERROR". Link the two time pickers with the sync button, so both panes always show the same time range.[13]

    Left: the ratio jumps. Right: the lines from the same minutes, every one saying "path":"/boom","status":500. Drag across the spike in the left graph to zoom: the right pane follows. Stop the loop with Ctrl+C and watch both sides calm down.

    From symptom to cause in three clicks: that is what observability is. The metric tells you when and how bad; the log tells you which request and why. The shared labels (app, namespace, pod) are what make the jump easy, which is why Alloy copies the same Kubernetes metadata Prometheus uses.

If you meet Promtail

Before Alloy, the usual Loki agent was Promtail. It reached end of life on 2 March 2026 and is no longer maintained.[14][15] You will still find it in clusters you inherit. Alloy can translate its config for you: alloy convert --source-format=promtail. Try it with a tiny Promtail config, using the alloy binary inside your Alloy Pod:

promtail.yaml
clients:
  - url: http://loki.monitoring:3100/loki/api/v1/push
scrape_configs:
  - job_name: pods
    kubernetes_sd_configs:
      - role: pod
    relabel_configs:
      - source_labels: [__meta_kubernetes_namespace]
        target_label: namespace
      - source_labels: [__meta_kubernetes_pod_name]
        target_label: pod
kubectl -n monitoring exec -i ds/alloy -c alloy -- alloy convert --source-format=promtail -o /dev/stdout /dev/stdin < promtail.yaml
Expected output (trimmed) 
discovery.kubernetes "pods" {
	role = "pod"

	selectors {
		role  = "pod"
		field = "spec.nodeName=" + coalesce(sys.env("HOSTNAME"), constants.hostname)
	}
}

discovery.relabel "pods" {
	targets = discovery.kubernetes.pods.targets
	...
}

loki.source.file "pods" {
	targets    = discovery.relabel.pods.output
	forward_to = [loki.write.default.receiver]
	...
}

loki.write "default" {
	endpoint {
		url = "http://loki.monitoring:3100/loki/api/v1/push"
	}
	external_labels = {}
}

Almost your config. One difference: the converted config uses loki.source.file, which reads the log files under /var/log/pods on the node, the way Promtail did. Yours uses loki.source.kubernetes, which reads through the Kubernetes API. Both are valid. Reading files needs the node's log folder mounted into the Alloy Pod; reading through the API needs no node access but costs more network traffic and kubelet CPU.[6]

The releases are gone, the CRDs are not. That is on purpose: Helm does not upgrade or delete CRDs, "due to the danger for unintentional data loss".[16] Deleting a CRD deletes every custom resource of that type, everybody's ServiceMonitors included, so Helm leaves that decision to you. On your own kind cluster, just delete the whole cluster:

kind delete cluster
