Instrument your server, query it, graph it, alert on it

Your win: your own code produces metrics. Prometheus finds them because of a ServiceMonitor you wrote. A Grafana dashboard shows Rate, Errors and Duration, and an alert you wrote fires.

Before this: lesson 04, so kube-prometheus-stack runs in the monitoring namespace and you know why a ServiceMonitor needs the label release: kps. Your hello repository has main.go, a multi-stage Dockerfile (session 1, lesson 04) and k8s/ (session 1, lesson 08). Work in your hello repository. The finished files are in the course repository under examples/s3/hello-0.2.0/ and examples/s3/k8s/.

The chain you are building

Five links, each one yours by the end of this lesson:

  1. Your Go code counts and times every request, and serves the numbers at /metrics.
  2. A ServiceMonitor tells the operator: scrape the Service hello, on the port named http.
  3. Prometheus scrapes every Pod every 15 seconds and stores the numbers as time series.
  4. Grafana asks Prometheus questions in PromQL and draws the answers.
  5. A PrometheusRule asks one question over and over. When the answer is "bad" for long enough, Alertmanager gets an alert.

Two metric types are enough

Prometheus clients offer a few metric types. You need two:[1]

  • A counter only goes up. It resets to zero only when the process restarts. Use it for things that happen: requests served, errors returned.
  • A histogram sorts each observation into buckets, such as "under 5 ms", "under 10 ms", and so on. Each bucket is itself a counter. It also keeps a count and a sum of all observations. Use it for sizes and durations, so you can later ask "how slow were the slowest 5 %?"

Names follow conventions.[2] A counter ends in _total. A name carries its unit, and the unit is a base unit: seconds, not milliseconds; bytes, not megabytes. So you will create http_requests_total and http_request_duration_seconds.

Labels, and the cardinality trap

A label splits one metric into several time series, such as http_requests_total{path="GET /", status="200"}. Every distinct combination of label values is a separate series, and each series costs Prometheus memory, CPU and disk.[2] The docs advise keeping most metrics below about ten series.[3]

So never put an unbounded value in a label: not the raw URL, not a user ID, not a request ID. Picture labelling by raw URL. Anyone who sends /a1, /a2, /a3… creates a new series with each request, until Prometheus runs out of memory.

Your server already has a bounded value at hand. Since Go 1.22, http.ServeMux matches patterns such as GET /healthz, and it records the pattern that matched in r.Pattern.[4] You wrote three patterns, so the label can have only a handful of values, whatever URLs the world sends.

RED: three questions for every service

For a service that answers requests, watch three things. The RED method names them:[5]

LetterThe questionYour metric
RateHow many requests per second?http_requests_total
ErrorsHow many of those fail?http_requests_total, status 5xx
DurationHow long do they take?http_request_duration_seconds

The Prometheus docs make the same point: for an online-serving system, the key metrics are requests, errors and latency.[3]

Two PromQL functions

A counter's raw value is "requests since this process started". That number only grows, and it drops to zero on every restart, so a graph of it says little. rate(counter[1m]) gives the per-second average increase over the last minute. It also adjusts for counter resets, so a restart does not show up as a dip.[6]

A window must hold at least two scrapes. At one scrape every 15 seconds, [1m] holds four. This lab is short, so it uses [1m]. In production, [5m] is the usual choice: smoother, and less sensitive to one missed scrape.

histogram_quantile(0.95, …) estimates the 95th percentile from the buckets: 95 % of requests were faster than this. It cannot know the exact durations, only the bucket counts. So it assumes the observations are spread evenly inside a bucket, and interpolates. The answer is only as precise as your buckets.[7]

An alert waits before it fires

An alerting rule is a PromQL expression that Prometheus evaluates again and again. If it returns a result, the alert is active. With for: 2m it first goes pending, and it turns firing only when the condition has held for two whole minutes.[8] One bad scrape, or a short burst of errors, never wakes anyone up. Only firing alerts go to Alertmanager, which groups them and sends notifications.

Prometheus picks up a PrometheusRule the same way it picks up a ServiceMonitor: by label. The stack's Prometheus has ruleSelector: {matchLabels: {release: kps}}, the twin of the serviceMonitorSelector from lesson 04.[9] Forget the label and your rule is silently ignored.

Do it

You will need several terminals: each port-forward keeps its terminal busy until you press Ctrl+C.

  1. Add the Prometheus client library to your module. go get adds it to go.mod; go mod tidy adds what that library needs in turn and writes the checksums to go.sum.[10]

    go get github.com/prometheus/client_golang@latest
    Expected output (trimmed) 
    go: added github.com/prometheus/client_golang v1.25.0

    Do not run go mod tidy yet. Your code does not import the library, so tidy would remove it again. First the code.

  2. Replace main.go. Read it all before you save it.

    main.go

    package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
	"strconv"
	"time"

	"github.com/prometheus/client_golang/prometheus"
	"github.com/prometheus/client_golang/prometheus/promauto"
	"github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
	requests = promauto.NewCounterVec(prometheus.CounterOpts{
		Name: "http_requests_total",
		Help: "HTTP requests, by route and status code.",
	}, []string{"path", "status"})
	duration = promauto.NewHistogramVec(prometheus.HistogramOpts{
		Name:    "http_request_duration_seconds",
		Help:    "HTTP request latency, by route.",
		Buckets: prometheus.DefBuckets,
	}, []string{"path"})
)

// statusRecorder remembers the status code the handler wrote.
type statusRecorder struct {
	http.ResponseWriter
	status int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code)
}

// instrument counts and times every request. It labels by the route
// pattern ("GET /"), never by the raw URL, so the label set stays small.
func instrument(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
		next.ServeHTTP(rec, r)
		requests.WithLabelValues(r.Pattern, strconv.Itoa(rec.status)).Inc()
		duration.WithLabelValues(r.Pattern).Observe(time.Since(start).Seconds())
	})
}

func main() {
	port := os.Getenv("PORT")
	if port == "" {
		port = "8080"
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "hello from my container")
	})
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	mux.HandleFunc("GET /boom", func(w http.ResponseWriter, r *http.Request) {
		http.Error(w, "boom", http.StatusInternalServerError)
	})
	mux.Handle("GET /metrics", promhttp.Handler())
	log.Printf("listening on :%s", port)
	log.Fatal(http.ListenAndServe(":"+port, instrument(mux)))
}

    What each part does:

    • promauto creates the two metrics and registers them with the library's default registry, so you never call a register function yourself.[11] NewCounterVec is a counter with labels path and status. NewHistogramVec is a histogram with label path. DefBuckets are the library's default buckets, from 5 ms up to 10 s.
    • statusRecorder wraps the ResponseWriter and notes the status code a handler writes. It starts at 200, because a handler that only writes a body never calls WriteHeader, and Go then sends 200.
    • instrument is middleware: a handler that wraps another handler. It starts a clock, lets the real handler run, then adds one to the counter and records the duration. The mux fills in r.Pattern while it routes the request, so once next.ServeHTTP returns, the pattern is there to read.
    • /boom always answers 500. It is a fault injector: a way to make errors on demand, so you can watch your graphs and your alert react.
    • /metrics is served by promhttp.Handler(), which prints every registered metric as text. It passes through the middleware too, so the scrapes themselves are counted.
    • The handlers now live on a mux of your own instead of the default one, so that the whole mux can be wrapped: instrument(mux).

    Now tidy, and check that it builds:

    go mod tidy
    go build ./...

    go.mod now lists client_golang v1.25.0 and a few indirect dependencies, and there is a new go.sum.

  3. Update the Dockerfile. Two lines are new compared with session 1: the build stage copies go.sum along with go.mod, and downloads the modules before it copies your code. Dependencies change rarely, so that download is a cached layer. Changing main.go only rebuilds the steps after COPY . ..

    Dockerfile

    FROM golang:1.27 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -o /server .

FROM gcr.io/distroless/static-debian13:nonroot
COPY --from=build /server /server

    This file leaves out the /data volume from session 1, because the server never writes there. If you kept it, you may leave those lines in. Keep your .dockerignore too, so COPY . . does not copy .git.

    Build the new version and copy it into your kind cluster, as in session 1:

    docker build -t hello:0.2.0 .
    kind load docker-image hello:0.2.0

  4. Name the port. A ServiceMonitor refers to a Service port by its name, not by its number.[12] In k8s/deployment.yaml, change the image to hello:0.2.0 and give the container port the name http. Two replicas are enough here, and they save memory for the monitoring stack.

    k8s/deployment.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 2
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: hello:0.2.0
          ports:
            - name: http
              containerPort: 8080

    If your file has the resources and probes from session 1, lesson 08, keep them. The file above shows only what this lesson needs.

    In k8s/service.yaml, name the Service port http too, and point targetPort at the container port's name:

    k8s/service.yaml

    apiVersion: v1
kind: Service
metadata:
  name: hello
  labels:
    app: hello
spec:
  selector:
    app: hello
  ports:
    - name: http          # the ServiceMonitor finds the port by this name
      port: 80
      targetPort: http

    Note the new labels on the Service itself. A ServiceMonitor selects Services by their labels, not Pods.

  5. Write the ServiceMonitor. Copy the release: kps label exactly: without it, lesson 04 showed you, nothing happens and nothing complains.

    k8s/servicemonitor.yaml

    apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: hello
  labels:
    release: kps          # the label the stack's Prometheus selects on
spec:
  selector:
    matchLabels:
      app: hello          # Services with this label
  endpoints:
    - port: http          # the Service port *name*
      path: /metrics
      interval: 15s
    kubectl apply -f k8s/
    Expected output 
    deployment.apps/hello created
service/hello created
servicemonitor.monitoring.coreos.com/hello created

    If you already had hello running, you see configured instead of created for the Deployment and the Service.

  6. Try the server. In a second terminal, forward a local port to the Service:

    kubectl port-forward svc/hello 8080:80

    Back in the first terminal, make one normal request, one error, and one request to a path you never defined. Then read the metrics.

    curl localhost:8080/
    curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/boom
    curl localhost:8080/nope
    curl -s localhost:8080/metrics | grep -E '^http_requests_total|^http_request_duration_seconds_count'
    Expected output 
    hello from my container
500
hello from my container
http_request_duration_seconds_count{path="GET /"} 2
http_request_duration_seconds_count{path="GET /boom"} 1
http_requests_total{path="GET /",status="200"} 2
http_requests_total{path="GET /boom",status="500"} 1

    Look at the count for GET /: 2. The pattern GET / catches every path no other pattern claims, so /nope was counted there. There is no /nope series, and no URL anyone sends can create one. That is the cardinality rule, working.

    A request that matches no pattern at all, such as a POST, gets an empty r.Pattern.[4] It is counted with path="": one more series, still bounded.

  7. Make traffic. In a third terminal, start a loop that sends one good request and one failing request, five times a second. Leave it running.

    while true; do curl -s -o /dev/null localhost:8080/; curl -s -o /dev/null localhost:8080/boom; sleep 0.2; done

    Half of these requests fail. That is far above any sane error budget, which is the point: your alert will catch it.

  8. Open Prometheus. In a fourth terminal:

    kubectl -n monitoring port-forward svc/kps-prometheus 9090:9090

    Open http://localhost:9090, then Status → Target health. Find the pool serviceMonitor/default/hello/0. It can take up to a minute to appear, as in lesson 04.

    Expected targets: job, pod, state (your Pod names differ) 
    hello   hello-f5645869f-4c29l   up
hello   hello-f5645869f-lzr4c   up

    Two targets: one per Pod, at the Pod's own IP. The operator follows the Service's EndpointSlices, so Prometheus scrapes every Pod, not the Service. The job label is the Service's name. Now, on the Query page, run:

    http_requests_total{job="hello", path="GET /metrics"}
    Expected output (one of two series) 
    http_requests_total{container="hello", endpoint="http", instance="10.244.0.26:8080", job="hello", namespace="default", path="GET /metrics", pod="hello-f5645869f-4c29l", service="hello", status="200"}

    Your code set two labels, path and status. The rest were added by Prometheus from the ServiceMonitor: where the series came from.

  9. Ask the four RED questions. Run each query on the Query page. Wait two minutes after starting the loop, so each one-minute window is full.

    Rate, per series:

    rate(http_requests_total{job="hello"}[1m])
    Expected output (path, status, pod, requests per second) 
    GET /         200   hello-...-4c29l   7.73
GET /boom     500   hello-...-4c29l   7.73
GET /metrics  200   hello-...-4c29l   0.0667
GET /metrics  200   hello-...-lzr4c   0.0667

    Look at the pods. All your traffic went to 4c29l; lzr4c only saw the scrapes, one every 15 seconds (1/15 = 0.0667 per second). kubectl port-forward svc/hello does not balance load: it picks one Pod behind the Service and tunnels to it. Real traffic, through the Service's cluster IP, would be spread over both.

    Rate, summed by status. sum by (status) adds up the series and keeps only the status label:

    sum by (status) (rate(http_requests_total{job="hello"}[1m]))
    Expected output 
    {status="200"}   7.87
{status="500"}   7.73

    Errors, as a ratio of all requests:

    sum(rate(http_requests_total{job="hello", status=~"5.."}[1m])) / sum(rate(http_requests_total{job="hello"}[1m]))
    Expected output 
    0.4957

    Almost exactly half. Slightly under, because the scrapes of /metrics are successful requests too. =~"5.." is a regular expression: any status from 500 to 599.

    Duration, the 95th percentile:

    histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{job="hello"}[1m])))
    Expected output (seconds) 
    0.00475

    4.75 ms. Each bucket is a series of its own, labelled le ("less than or equal"). sum by (le) merges the Pods and routes but keeps the buckets apart, which is what histogram_quantile needs.[7] Your requests really take far less than a millisecond. They all fall into the lowest bucket, 0 to 5 ms, and interpolation inside it gives 4.75 ms. Buckets set the precision.

  10. Put the three answers on a dashboard. In a fifth terminal, forward Grafana, then read the admin password from its Secret:

    kubectl -n monitoring port-forward svc/kps-grafana 3000:80
    kubectl -n monitoring get secret kps-grafana -o jsonpath='{.data.admin-password}' | base64 -d

    Open http://localhost:3000 and log in as admin with that password. Then:

    1. Dashboards → New → New dashboard → Add visualization, and pick the Prometheus data source.
    2. Switch the query editor to Code, paste the rate query summed by status, and give the panel the title Rate.
    3. Add a second panel with the error ratio, title Errors, and a third with the 95th percentile, title Duration p95. In the panel options you can set the unit to "Percent (0.0-1.0)" and "seconds".
    4. Save the dashboard as hello.

    A dashboard you clicked together lives only in Grafana's database. Put it in Git. Open Export on the dashboard and export it as JSON. (Newer Grafana versions call this Export as code, with the "Classic" model.)[13] Save the file as dashboards/hello.json in your repository.

    Optional: let Grafana load the file by itself. The stack's Grafana Pod runs a sidecar container that watches for ConfigMaps labelled grafana_dashboard=1, and loads the JSON inside them as dashboards. Every built-in dashboard of the stack arrives this way: kubectl -n monitoring get cm -l grafana_dashboard=1 lists them. So a ConfigMap in monitoring holding your hello.json, with that label, puts your dashboard back after any reinstall. It is one more watch loop, like the operators from lesson 02 of this session.

  11. Write the alert. Fire when more than 5 % of requests fail, for two minutes straight. The expression is your error ratio with a threshold.

    k8s/prometheusrule.yaml

    apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: hello
  labels:
    release: kps
spec:
  groups:
    - name: hello
      rules:
        - alert: HelloHighErrorRate
          expr: |
            sum(rate(http_requests_total{job="hello", status=~"5.."}[1m]))
              /
            sum(rate(http_requests_total{job="hello"}[1m])) > 0.05
          for: 2m
          labels:
            severity: warning
          annotations:
            summary: "More than 5% of hello requests fail"
    kubectl apply -f k8s/prometheusrule.yaml
    Expected output 
    prometheusrule.monitoring.coreos.com/hello created

    The > 0.05 is a filter: the expression returns a result only while the ratio is above 0.05. A result means "active". severity is a label that Alertmanager can use to route the alert, and summary is the text a human reads.

  12. Watch it fire. Your loop is still running, so the ratio is about 0.5. In Prometheus, open Alerts and find HelloHighErrorRate. Reload every 15 seconds or so. Once the operator has loaded the rule (up to a minute), the alert goes from inactive to pending, and two minutes after that to firing.

    Expected output (our run, checked every 15 seconds) 
    t=15s..75s  state=pending  activeAt=09:31:06
t=90s       state=firing

    We started checking about half a minute after the rule became active at 09:31:06. It was pending until the full two minutes had passed since then, and firing on the next check. Now look at Alertmanager. In one more terminal:

    kubectl -n monitoring port-forward svc/kps-alertmanager 9093:9093

    Open http://localhost:9093.

    Expected alerts 
    HelloHighErrorRate   active
Watchdog             active

    Watchdog always fires, on purpose. It is a dead man's switch: if it ever stops arriving somewhere, you know the alerting pipeline itself is broken.

  13. Stop the loop with Ctrl+C. Within a minute, no /boom requests are left in the one-minute window, the ratio drops to 0, and the expression returns nothing. The alert turns inactive in Prometheus and disappears from Alertmanager's active list.

    git add main.go go.mod go.sum Dockerfile k8s/ dashboards/hello.json
    git commit -m "Instrument hello with Prometheus metrics, add ServiceMonitor, alert and dashboard"
    git push
