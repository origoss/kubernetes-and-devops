The operator pattern: new nouns and a loop that never stops

Your win: you can explain, in one sentence, why an operator keeps working even when it misses an event. You can tell a CRD from a CR, and you know which part of the cluster acts on each.

Before this: Helm as a consumer, and the self-healing step of lesson 07, where you deleted a Pod and watched a new one appear. Your kind cluster runs.

What a Deployment cannot do

A Deployment keeps N copies of a Pod running. That is all it knows. It does not know that your database has a primary and two replicas, and that when the primary dies one replica must be promoted, and the others told to follow it. It does not know that a certificate expires on Friday and must be renewed first. It does not know that a new Service just appeared and your monitoring should start watching it.

Today a person knows these things. "Human operators who look after specific applications and services have deep knowledge of how the system ought to behave, how to deploy it, and how to react if there are problems."[1] First that knowledge lives in their head, then in a runbook: "when X happens, do Y". An operator is that runbook turned into a program that runs in the cluster, all day.

The official definition: "Operators are software extensions to Kubernetes that make use of custom resources to manage applications and their components. Operators follow Kubernetes principles, notably the control loop."[1] Two ideas in that sentence: custom resources and the control loop. You already know half of each.

You already met a controller

In lesson 07 you deleted a hello Pod, and a new one was Pending in the same second. Nobody called the ReplicaSet controller. It watched, counted the Pods that matched its selector, saw one where it wanted two, and made one. "Controllers are control loops that watch the state of your cluster, then make or request changes where needed."[2]

An operator is the same kind of loop, with two differences. It runs as an ordinary Pod that someone installed, not inside the control plane. And it looks after new nouns: not Pods and ReplicaSets, but things like "a Prometheus server" or "a database cluster".

New nouns: CRD and CR

The Kubernetes API has a fixed set of nouns: Pod, Service, Deployment, ConfigMap, and a few dozen more. A CustomResourceDefinition (CRD) adds a new one. "When you create a new CustomResourceDefinition (CRD), the Kubernetes API Server creates a new RESTful resource path".[3] From then on, kubectl get, apply and delete work on the new noun like on any built-in one.

A custom resource (CR) is one object of that new noun.[4] Remember lesson 01: an image is the class, a container is an object. Here it is the same:

DefinesExample from the session
CRDa new kind: its name and the schema of its fields (the class)servicemonitors.monitoring.coreos.com
CRone object of that kind, with your values (the object)a ServiceMonitor named podinfo: "scrape the podinfo Service"

The CRD carries a schema, so the API server checks every CR you apply against it, and kubectl explain can describe its fields.[3] But a CRD alone does nothing. The API server stores your CR in etcd, and that is all. Something has to read it and act. That something is the operator. "When you combine a custom resource with a custom controller, custom resources provide a true declarative API."[4]

The control loop

   you ──kubectl apply──►  CR: the desired state, stored by the API server
                                │
                                │ watch
                                ▼
                          ┌────────────┐   act    ┌─────────────────────┐
             ┌──────────► │  operator  │ ───────► │  the real things:   │
             │            │  (a Pod)   │          │  Pods, config,      │
             │            └────────────┘ ◄─────── │  Secrets, ...       │
             │                  │       observe   └─────────────────────┘
             └──── repeat ──────┘
               1 observe   what is actually there?
               2 diff      desired (the CR) vs actual
               3 act       close the gap, nothing more
               4 repeat    on every change, often on a timer too

This is the thermostat from lesson 05: you set the desired temperature, it measures the actual one, and it switches the heating to close the gap.[2] It never finishes. The loop runs for as long as the operator runs.

Level-triggered, not edge-triggered

There are two ways to build such a loop.

  • Edge-triggered: react to each change. "A ServiceMonitor was added, so add one scrape job." Like a doorbell: if you are in the shower when it rings, you never learn someone came.
  • Level-triggered: react to the state. "Here are all ServiceMonitors that exist now; here is the config that exists now; make the config match." Like checking the mailbox: whatever arrived while you were away is still in there.

Kubernetes controllers, operators included, are level-triggered. Change events only wake them up; what they act on is the whole desired state and the whole actual state. Learn this sentence:

Remember: an operator that misses an event still converges on the next pass, because it compares whole states, not events.

That is why an operator can crash, restart or be switched off for an hour and still catch up. "Controllers can fail, so Kubernetes is designed to allow for that."[2] It also means hand edits do not stick: if you change something the operator owns, the next pass sees a gap and puts it back.

One more property follows. The loop will run the "act" step many times on the same state, so the step must be idempotent: running it twice has the same effect as running it once. "Make sure the config contains job X" is idempotent. "Append job X to the config" is not; after ten passes you have ten copies. You have seen this already: kubectl apply and helm upgrade --install are idempotent too.

Coming up in the session

In the session you install kube-prometheus-stack with Helm. It brings the Prometheus Operator and ten CRDs, among them Prometheus and ServiceMonitor. You write a ServiceMonitor, and the operator turns it into Prometheus configuration for you. Then you switch the operator off, apply another ServiceMonitor, and watch nothing happen: the CR is stored, and nobody acts on it. Switch it back on, and it catches up. That is the sentence above, live.

This course only uses operators. Writing one is a course of its own: you would use a framework such as kubebuilder or the Operator SDK, usually in Go. The Kubernetes page on the operator pattern lists kubebuilder and other such tools.[1]

Do it

Three short looks at the API of your own kind cluster.

  1. List the custom nouns your cluster knows.

    kubectl get crd
    Expected output 
    No resources found

    None. A fresh kind cluster has only built-in nouns, and podinfo from the last lesson brought no CRDs. After the install in the session, this command lists ten, all ending in monitoring.coreos.com.

  2. List the built-in nouns. Every row is a kind of object you can get, apply and delete.

    kubectl api-resources | head
    Expected output 
    NAME                                SHORTNAMES   APIVERSION                        NAMESPACED   KIND
bindings                                         v1                                true         Binding
componentstatuses                   cs           v1                                false        ComponentStatus
configmaps                          cm           v1                                true         ConfigMap
endpoints                           ep           v1                                true         Endpoints
events                              ev           v1                                true         Event
limitranges                         limits       v1                                true         LimitRange
namespaces                          ns           v1                                false        Namespace
nodes                               no           v1                                false        Node
persistentvolumeclaims              pvc          v1                                true         PersistentVolumeClaim

    Run it without | head to see them all, and find deployments (group apps/v1). The short names explain kubectl get cm and kubectl get svc. After the session, the new kinds show up in this same list.

  3. Ask the API to explain one field. This works because every kind has a schema.

    kubectl explain deployment.spec.replicas
    Expected output 
    GROUP:      apps
KIND:       Deployment
VERSION:    v1

FIELD: replicas <integer>


DESCRIPTION:
    Number of desired pods. This is a pointer to distinguish between explicit
    zero and not specified. Defaults to 1.

    "Number of desired pods": the field is desired state, and a controller makes it real. A CRD carries a schema of the same kind, so in the session kubectl explain servicemonitor.spec works just the same.
