Session 1 · Kubernetes · about 35 minutes · do it after the session

Is your server healthy, and how much may it use?

Your win: your Deployment declares requests, a memory limit and all three probes. You have seen each of them go wrong on purpose, and you can say what Kubernetes does when a Pod is out of memory, not ready, stuck, or told to stop.

Before this: lesson 07, so your k8s/deployment.yaml (3 replicas of hello:0.1.1) and k8s/service.yaml are applied and committed, and you can read Events bottom-up (lesson 06). Work in your hello repository, except where a step says to use the course repository.

Two numbers, two different jobs

For each container you can set two amounts of CPU and memory:[1]

  • requests are used before the Pod runs. The scheduler places a Pod only on a node that still has that much unreserved capacity. A request is a reservation. It is not a cap: the container may use more if the node has it spare.
  • limits are enforced while the container runs, by the Linux kernel's cgroups, which you met in lesson 01. Go over the memory limit and the kernel kills the process (OOM, "out of memory"). Go over a CPU limit and the process is only slowed down, never killed.

A request can never be larger than its limit. The API refuses such a Pod.

Units

  • Memory is in bytes, usually written with a suffix. Mi is a mebibyte (1024 × 1024 bytes) and Gi a gibibyte. Mind the case: M means a million bytes, and a lowercase m on memory means thousandths of a byte, which is never what you want.[1]
  • CPU is in cores, and m means millicores. 50m is one twentieth of a core, and 1 is a whole core.

Your Go server idles at about 1.5 MB of memory and almost no CPU, so small values are honest values. We set a CPU request but no CPU limit: going over a CPU limit would only slow the server down, and the request already keeps the scheduler honest.

QoS classes: who goes first when memory runs out

From your requests and limits, Kubernetes puts every Pod into a Quality of Service class. When a node runs short of memory, the kubelet evicts Pods to save the node, and the class decides the order.[2]

ClassWhenEvicted
BestEffortno requests and no limits at allfirst
Burstablesome requests or limits, but not the Guaranteed recipenext, those using most above their request first
Guaranteedevery container has CPU and memory requests equal to its limitslast

Everything you ran in lesson 07 was BestEffort: the first to go.

Three probes, three questions

The kubelet keeps asking your container questions. A probe is one of those questions, here an HTTP GET: any status from 200 to 399 counts as a yes. Kubernetes has three kinds, and each "no" leads to a different action:[3]

ProbeThe questionWhen it fails
startupProbeHas the app finished starting?After failureThreshold misses the container is restarted. Until it succeeds, the other two probes do not run at all.
readinessProbeShould this Pod get traffic right now?The Pod is marked not ready in the Service's EndpointSlice and gets no traffic. Nothing is restarted; it gets traffic again once it passes.
livenessProbeIs the process stuck beyond repair?The container is restarted, with SIGTERM first.

Every probe has the same timing knobs.[4] periodSeconds (default 10) is how often it asks. timeoutSeconds (default 1) is how long one answer may take. failureThreshold (default 3) is how many misses in a row count as failure. initialDelaySeconds is how long to wait before the first question. A startup probe gives a slow app failureThreshold × periodSeconds to come up: 30 × 10 is a 5-minute budget. Without one, the only way to protect a slow starter is a long delay on liveness, which also delays catching real failures.

Readiness guards your rollouts

A rolling update removes an old Pod only when a new one is ready. By default it may run 25 % more Pods than replicas during the update, and have at most 25 % unavailable (maxSurge, maxUnavailable).[5] So a readiness probe is more than a traffic switch: it is the check that stops a bad version from replacing a good one. In lesson 07 a missing image stopped the rollout; a new version that starts but never becomes ready stops it just the same.

Stopping gracefully

When a Pod is deleted, by you, a rollout or a scale-down, two things start at once: the Pod is taken out of the Service's EndpointSlice, so new traffic stops arriving, and the kubelet sends SIGTERM to PID 1 in each container. Then it waits up to terminationGracePeriodSeconds, 30 by default. Whatever still runs after that gets SIGKILL, which cannot be caught.[6] A well-behaved server uses those seconds to finish the requests it is already serving, then exits 0. Yours does not yet: Go ends it at once on SIGTERM, which is the Error you saw in lesson 07. The homework fixes that.

The classic mistake

A liveness probe that checks a dependency. Picture /healthz asking the database: the database goes down, every replica fails liveness, and Kubernetes restarts all of them, over and over. Restarting your server fixes nothing about the database, and now you have two outages. Liveness asks about this process only. "The database is down, stop sending me traffic" belongs in readiness, if anywhere.[3]

Do it

  1. Before you change anything, check the QoS class of your Pods:

    kubectl get pods -l app=hello -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
    Expected output 
    NAME                     QOS
hello-646b86479c-7mpw4   BestEffort
hello-646b86479c-92zx6   BestEffort
hello-646b86479c-ds96t   BestEffort

  2. Add a resources block to the container in k8s/deployment.yaml, at the same depth as ports.

    k8s/deployment.yaml

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello
  labels:
    app: hello
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello
  template:
    metadata:
      labels:
        app: hello
    spec:
      containers:
        - name: hello
          image: hello:0.1.1
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 16Mi
            limits:
              memory: 62Mi
    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    Expected output (trimmed) 
    deployment.apps/hello configured
service/hello unchanged
Waiting for deployment "hello" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "hello" rollout to finish: 1 old replicas are pending termination...
deployment "hello" successfully rolled out

    Changing the Pod template made the Deployment replace every Pod, a few at a time: a rolling update, as in lesson 07.

  3. Check what the new Pods received. Use one of your Pod names.

    Expected output (trimmed) 
        Limits:
      memory:  62Mi
    Requests:
      cpu:        50m
      memory:     16Mi

    The server runs fine within 62 Mi. And the Pods changed class:

    kubectl get pods -l app=hello -o custom-columns=NAME:.metadata.name,QOS:.status.qosClass
    Expected output 
    NAME                     QOS
hello-c599d44c-9vqz8     Burstable
hello-c599d44c-mgqwt     Burstable
hello-c599d44c-mrt2v     Burstable

    Requests are set, but they differ from the limits (and there is no CPU limit), so the class is Burstable.

  4. Now break it on purpose: a memory limit far too small. Set both memory values to 2Mi. Both, because a request larger than its limit is refused. Try it with only the limit changed and you get:

    The Deployment "hello" is invalid: spec.template.spec.containers[0].resources.requests: Invalid value: "16Mi": must be less than or equal to memory limit of 2Mi

    With both at 2Mi, apply and watch:

    kubectl apply -f k8s/
    kubectl get pods -w
    Expected output (after about 20 seconds; stop with Ctrl+C) 
    NAME                     READY   STATUS              RESTARTS      AGE
hello-5b6b65946-c24cf    0/1     ContainerCreating   0             0s
hello-8677475c9f-7kx8q   1/1     Running             0             7s
hello-8677475c9f-bbgwd   1/1     Running             0             7s
hello-8677475c9f-hs4fs   1/1     Running             0             6s
hello-5b6b65946-c24cf    0/1     RunContainerError   0             1s
hello-5b6b65946-c24cf    0/1     RunContainerError   1 (1s ago)    2s

    Two things to notice. The new Pod flips between RunContainerError and CrashLoopBackOff, with restarts climbing. And your three old Pods are still running: the rolling update waits for each new Pod to become ready, and this one never does. kubectl get deploy hello shows READY 3/3 but UP-TO-DATE 1. Your server is still up, running the old settings.

  5. Find the cause with describe on the failing Pod.

    kubectl describe pod hello-5b6b65946-c24cf
    Expected output (trimmed) 
        State:          Waiting
      Reason:       RunContainerError
    Last State:     Terminated
      Reason:       StartError
      Message:      failed to create containerd task: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: container init was OOM-killed (memory limit too low?)
      Exit Code:    128
...
Events:
  Type     Reason     Age                From     Message
  ----     ------     ----               ----     -------
  Normal   Created    11s (x4 over 1m)   kubelet  spec.containers{hello}: Container created
  Warning  Failed     11s (x4 over 1m)   kubelet  spec.containers{hello}: Error: failed to create containerd task: ... container init was OOM-killed (memory limit too low?)
  Warning  BackOff    11s (x3 over 1m)   kubelet  spec.containers{hello}: Back-off restarting failed container hello in pod ...

    "container init was OOM-killed (memory limit too low?)": the kernel killed the process before your server even started, because 2 Mi is not enough to start any process at all. kubectl logs has nothing to show here, because your program never ran.

    A server that starts fine and then grows past its limit fails differently: the Last State says Reason: OOMKilled with Exit Code: 137, and it ends in CrashLoopBackOff too.[1]

  6. Break it the other way: ask for far more than your laptop has. Set both memory values to 100Gi, then apply and look.

    kubectl apply -f k8s/
    kubectl get pods
    Expected output 
    NAME                     READY   STATUS    RESTARTS   AGE
hello-8677475c9f-7kx8q   1/1     Running   0          58s
hello-8677475c9f-bbgwd   1/1     Running   0          58s
hello-8677475c9f-hs4fs   1/1     Running   0          57s
hello-86c79c5c6-fg6rc    0/1     Pending   0          6s
    kubectl describe pod hello-86c79c5c6-fg6rc
    Expected output (only the Events) 
    Events:
  Type     Reason            Age              From               Message
  ----     ------            ----             ----               -------
  Warning  FailedScheduling  5s (x2 over 6s)  default-scheduler  0/1 nodes are available: 1 Insufficient memory. preemption: 0/1 nodes are available: 1 Preemption is not helpful for scheduling.

    This time the container never got near a kernel. The scheduler found no node with 100 Gi unreserved, so the Pod waits in Pending. It stays there until you lower the request or a big enough node joins. Note who reported it: default-scheduler, not kubelet. Requests are the scheduler's business.

    One more face of the same mistake, for the record. A ridiculously small limit such as 1Ki does not produce an OOM kill at all. The Pod hangs in ContainerCreating, and its Events repeat FailedMount ... no space left on device. Kubernetes mounts a small in-memory volume into every Pod, and that volume is sized by the memory limit, so with 1 KiB there is no room for even that. Same root cause, a misleading symptom: always check the resources when a message makes no sense.

  7. Restore the working values: requests cpu: 50m and memory: 16Mi, limit memory: 62Mi. Then apply and confirm.

    kubectl apply -f k8s/
    kubectl rollout status deployment/hello
    kubectl get pods
    Expected output 
    deployment.apps/hello configured
service/hello unchanged
deployment "hello" successfully rolled out
NAME                     READY   STATUS    RESTARTS   AGE
hello-8677475c9f-7kx8q   1/1     Running   0          58s
hello-8677475c9f-bbgwd   1/1     Running   0          58s
hello-8677475c9f-hs4fs   1/1     Running   0          57s

    The broken Pod is gone, and the three good Pods kept running the whole time. The template matches the good one again, so the Deployment simply keeps them.

    You have now seen three faces of one kind of mistake: CrashLoopBackOff with a StartError, Pending with FailedScheduling, and a ContainerCreating that never ends. A misbehaving cluster rarely tells you which number is wrong; you have to read your way there.

  8. Now the probes. Add them to the container, at the same depth as resources. All three ask your /healthz on port 8080.

    k8s/deployment.yaml (the container part)
          containers:
        - name: hello
          image: hello:0.1.1
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 50m
              memory: 16Mi
            limits:
              memory: 62Mi
          startupProbe:           # until this passes, the other two wait
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 1
            failureThreshold: 10
          readinessProbe:         # failing: no traffic from the Service
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 5
          livenessProbe:          # failing: the container is restarted
            httpGet:
              path: /healthz
              port: 8080
            periodSeconds: 10
    kubectl apply -f k8s/
    kubectl rollout status deployment/hello

    Then describe one of the new Pods (use your own name):

    kubectl describe pod hello-57646c8f98-4nv4p
    Expected output (trimmed) 
        Liveness:     http-get http://:8080/healthz delay=0s timeout=1s period=10s successThreshold=1 failureThreshold=3
    Readiness:    http-get http://:8080/healthz delay=0s timeout=1s period=5s successThreshold=1 failureThreshold=3
    Startup:      http-get http://:8080/healthz delay=0s timeout=1s period=1s successThreshold=1 failureThreshold=10

    Your values, plus the defaults you did not write: timeout=1s, failureThreshold=3.

  9. Watch each probe fail. In the course repository folder, examples/s1-08/probe-demos.yaml holds three Pods running your hello:0.1.1. Each has one probe, and each asks port 9999, where nothing listens. ready-demo also carries the label app: hello, so your Service selects it.

    kubectl apply -f examples/s1-08/probe-demos.yaml

    Wait about 40 seconds, then:

    kubectl events --for pod/ready-demo
    kubectl events --for pod/live-demo
    kubectl events --for pod/start-demo

    kubectl apply -f k8s/
    kubectl rollout status deployment/hello --timeout=30s
    kubectl get pods -l app=hello
    kubectl get deploy hello
    Expected output 
    deployment.apps/hello configured
service/hello unchanged

NAME                     READY   STATUS    RESTARTS   AGE

    The new Pod runs, but never becomes ready, so the rollout stops after one: your three old Pods keep serving (AVAILABLE 3). Its Events say why: Readiness probe failed: ... :9999/healthz: connect: connection refused. Put the port back to 8080, apply, and the rollout finishes.

    Why a wrong port and not a wrong path? Try path: /ready and the probe passes: your server's GET / pattern catches every path no other pattern claims (lesson 02), and answers 200. A health endpoint that answers yes to everything is a trap. Check what your probe really reaches.

  11. Stopping. Look at the grace period, then time two deletions: one of your Pods, and a Pod whose PID 1 ignores SIGTERM (sleep as PID 1 has no handler for it, so the signal does nothing).

    kubectl get pod hello-57646c8f98-8cf8r -o jsonpath='{.spec.terminationGracePeriodSeconds}{"\n"}'
    time kubectl delete pod hello-57646c8f98-8cf8r
    kubectl run sleeper --image=busybox:1.37 -- sleep 3600
    time kubectl delete pod sleeper
    Expected output (trimmed) 
    30
pod "hello-57646c8f98-8cf8r" deleted from default namespace
real	0m0.90s
pod/sleeper created
pod "sleeper" deleted from default namespace
real	0m31.60s

    Your server went in under a second: Go exits at once on SIGTERM (too abruptly, as the homework will show, but at least it exits). sleeper ignored the signal, so Kubernetes waited the full 30 seconds and then sent SIGKILL. A process that ignores SIGTERM makes every rollout and every scale-down slow.

  12. Run git diff: it should show the resources block and the three probes, all on port 8080. Then commit and push.

    git add k8s/deployment.yaml
    git commit -m "Add resource requests, a memory limit and probes"
    git push
