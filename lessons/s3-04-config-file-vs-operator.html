Session 3 · Operators · about 30 minutes · after the session

Two ways to add a scrape target: edit the file, or write a ServiceMonitor

Your win: you added a scrape target twice: once by hand-editing Prometheus's config, once by writing a ServiceMonitor. You watched the operator do the work, then watched it stop when you switched it off. You can say what an operator buys you, and what it costs.

Before this: kube-prometheus-stack runs in your cluster from lesson 03, and you know the words CRD, control loop and level-triggered from lesson 02. You have the podinfo chart repository from lesson 01. Work in your own hello repository; the example files are in the course repository, in examples/s3/.

The same job, two ways

You want Prometheus to scrape one more app. That is one of the most common changes a monitoring setup ever sees. There are two ways to make it.

The traditional way. Prometheus reads one YAML file, prometheus.yml. You add a job to it, and then you tell Prometheus to read it again. Prometheus "can reload its configuration at runtime": either with a SIGHUP signal or with an HTTP POST to /-/reload, which only works when Prometheus was started with --web.enable-lifecycle. "If the new configuration is not well-formed, the changes will not be applied."[1] In Kubernetes that file usually comes from a ConfigMap mounted as a volume. The kubelet updates the mounted file by itself, but not at once: the delay "can be as long as the kubelet sync period + cache propagation delay".[2]

The operator way. You never touch prometheus.yml. You write a small ServiceMonitor object next to your app. The operator sees it, regenerates the whole config, and the config-reloader sidecar makes Prometheus load it. Operators are "software extensions to Kubernetes that make use of custom resources to manage applications and their components", following the control loop.[3]

Reading this, the second way sounds obviously better. Do both, and feel where the difference really is. It is not where you expect.

Do it, part A: the traditional way

  1. Put podinfo back; you removed it at the end of lesson 01. Two replicas, from the values file you already know. Copy the three files this lesson needs into your monitoring/ folder first (same course-repository path as in lesson 03):

    cp ../kubernetes-and-devops/examples/s3/values-podinfo.yaml ../kubernetes-and-devops/examples/s3/plain-prometheus/prometheus.yaml ../kubernetes-and-devops/examples/s3/servicemonitor-podinfo.yaml monitoring/
    helm upgrade --install demo podinfo/podinfo --version 6.17.0 -f monitoring/values-podinfo.yaml --wait

    podinfo serves Prometheus metrics on /metrics, port 9898, behind the Service demo-podinfo.

  2. Read the plain Prometheus. It is the S1 pattern: a ConfigMap and a Deployment, nothing else. The ConfigMap holds the whole prometheus.yml, and the Deployment mounts it at /etc/prometheus.

    monitoring/prometheus.yaml

    apiVersion: v1
kind: ConfigMap
metadata:
  name: plain-prometheus
  namespace: plain
data:
  prometheus.yml: |
    global:
      scrape_interval: 15s
    scrape_configs:
      - job_name: prometheus
        static_configs:
          - targets: ["localhost:9090"]
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: plain-prometheus
  namespace: plain
spec:
  replicas: 1
  selector:
    matchLabels:
      app: plain-prometheus
  template:
    metadata:
      labels:
        app: plain-prometheus
    spec:
      containers:
        - name: prometheus
          image: prom/prometheus:v3.16.0
          args:
            - --config.file=/etc/prometheus/prometheus.yml
            - --web.enable-lifecycle
          ports:
            - containerPort: 9090
          volumeMounts:
            - name: config
              mountPath: /etc/prometheus
      volumes:
        - name: config
          configMap:
            name: plain-prometheus

    Note --web.enable-lifecycle: without it, the reload endpoint you need in a minute does not exist.

    kubectl create namespace plain
    kubectl apply -f monitoring/prometheus.yaml
    kubectl -n plain rollout status deploy/plain-prometheus

  3. Port-forward in a second terminal. Use 9091, so it does not clash with the kps Prometheus on 9090:

    kubectl -n plain port-forward deploy/plain-prometheus 9091:9090

    Open http://localhost:9091 → Status → Target health. One target: Prometheus scraping itself. With jq you can watch the same list from the terminal; you will run this line many times:

    curl -s localhost:9091/api/v1/targets | jq -r '.data.activeTargets[] | "\(.labels.job) \(.health) \(.scrapeUrl)"'
    Expected output 
    prometheus up http://localhost:9090/metrics

  4. Edit the file. In monitoring/prometheus.yaml, add a second job under scrape_configs. Keep the indentation: it sits inside the prometheus.yml: | block, so it is YAML inside YAML.

        scrape_configs:
      - job_name: prometheus
        static_configs:
          - targets: ["localhost:9090"]
      - job_name: podinfo
        static_configs:
          - targets: ["demo-podinfo.default.svc:9898"]
    kubectl apply -f monitoring/prometheus.yaml
    Expected output 
    configmap/plain-prometheus configured
deployment.apps/plain-prometheus unchanged

    Now run the curl … | jq line again, or refresh the UI.

    Expected output 
    prometheus up http://localhost:9090/metrics

    Nothing. The ConfigMap in the API changed. The file inside the Pod did not, yet.

  5. Watch the file. Print it from inside the Pod; repeat every 15 seconds or so until the podinfo job shows up:

    kubectl -n plain exec deploy/plain-prometheus -- cat /etc/prometheus/prometheus.yml

    In our run the file changed after 61 seconds. That is the kubelet's periodic sync of mounted ConfigMaps, the delay the Kubernetes docs warn about.[2] Now check the targets once more.

    Expected output 
    prometheus up http://localhost:9090/metrics

    Still nothing. The file is new, but Prometheus read it at startup and does not watch it. Somebody has to tell it.

  6. Reload, by hand.

    curl -X POST localhost:9091/-/reload

    It prints nothing: success. Wait one scrape interval (15 seconds), then look again.

    Expected output 
    podinfo up http://demo-podinfo.default.svc:9898/metrics
prometheus up http://localhost:9090/metrics

    There it is, after three steps and more than a minute. Look at the address: it is the Service. Prometheus sees one target. It has no idea that two podinfo Pods sit behind it; each scrape lands on whichever Pod the Service picks.

  7. The typo. Add one misspelled line right under - job_name: podinfo, as if you wanted a different interval for this job:

          - job_name: podinfo
        scrape_intervall: 15s
        static_configs:
          - targets: ["demo-podinfo.default.svc:9898"]
    kubectl apply -f monitoring/prometheus.yaml
    Expected output 
    configmap/plain-prometheus configured
deployment.apps/plain-prometheus unchanged

    Accepted. To Kubernetes, prometheus.yml is one long string: nobody checks what is inside. Wait for the file to sync (the exec cat again, about a minute), then reload:

    curl -X POST localhost:9091/-/reload
    Expected output 
    failed to reload config: couldn't load configuration (--config.file="/etc/prometheus/prometheus.yml"): parsing YAML file /etc/prometheus/prometheus.yml: yaml: unmarshal errors:
  line 8: field scrape_intervall not found in type config.ScrapeConfig

    The good news: Prometheus refuses the new file and keeps running with the old one, so both targets stay up. The bad news: the broken file is now the one on disk. It is waiting for the next restart.

  8. Step on the landmine. Restart the Deployment, as anyone might do next week for an unrelated reason:

    kubectl -n plain rollout restart deploy/plain-prometheus
    kubectl -n plain get pods
    Expected output after about 25 seconds (names shortened) 
    NAME                       READY   STATUS             RESTARTS   AGE
plain-prometheus-…-old     1/1     Running            0          6m
plain-prometheus-…-new     0/1     CrashLoopBackOff   2          25s

    The new Pod reads the broken file at startup and exits; its status flips between Error and CrashLoopBackOff. The old Pod still serves, because the rolling update from session 1, lesson 07 only removes an old Pod once a new one is ready.[4] It saved you here. Without a Deployment, or after a node restart, your monitoring would simply be down.

  9. Clean up part A. Stop the 9091 port-forward with Ctrl+C, then:

    kubectl delete namespace plain

Do it, part B: the operator way

  1. Port-forward to the kps Prometheus in your second terminal, and keep it open:

    kubectl -n monitoring port-forward svc/kps-prometheus 9090:9090

    The operator writes its generated config into the Secret prometheus-kps-prometheus, gzipped. Define a small shell function to read it; you will use it many times. A new terminal forgets it, so run this line again there if needed.

    genconf() { kubectl -n monitoring get secret prometheus-kps-prometheus -o jsonpath='{.data.prometheus\.yaml\.gz}' | base64 -d | gunzip; }
    genconf | grep '^- job_name'
    Expected output 
    - job_name: serviceMonitor/monitoring/kps-alertmanager/0
- job_name: serviceMonitor/monitoring/kps-alertmanager/1
- job_name: serviceMonitor/monitoring/kps-apiserver/0
- job_name: serviceMonitor/monitoring/kps-coredns/0
- job_name: serviceMonitor/monitoring/kps-grafana/0
- job_name: serviceMonitor/monitoring/kps-kubelet/0
- job_name: serviceMonitor/monitoring/kps-kubelet/1
- job_name: serviceMonitor/monitoring/kps-kubelet/2
- job_name: serviceMonitor/monitoring/kps-operator/0
- job_name: serviceMonitor/monitoring/kps-prometheus/0
- job_name: serviceMonitor/monitoring/kps-prometheus/1

    Eleven jobs, one per ServiceMonitor endpoint. Nobody wrote this file by hand.

  2. Write a ServiceMonitor. Look at the podinfo Service first: the ServiceMonitor selects it by label and names its port.

    kubectl get svc demo-podinfo -o jsonpath='{.spec.ports[*].name} | {.metadata.labels.app\.kubernetes\.io/name}'
    Expected output 
    http grpc | demo-podinfo

    Now type this one yourself, as a new file monitoring/sm-first-try.yaml. It is the obvious version, and it has a bug:

    monitoring/sm-first-try.yaml

    apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: podinfo
  namespace: default
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: demo-podinfo
  endpoints:
    - port: http
      path: /metrics
    kubectl apply -f monitoring/sm-first-try.yaml
    Expected output 
    servicemonitor.monitoring.coreos.com/podinfo created

    Wait ten seconds, then look for it in the generated config:

    genconf | grep 'job_name: serviceMonitor/default'
    Expected output 
    (no output)

    Empty. No error from kubectl, no error in the UI, nothing in the operator log. It is silently ignored.

  3. The gotcha. Remember the selector from lesson 03:

    kubectl -n monitoring get prometheus kps-prometheus -o jsonpath='{.spec.serviceMonitorSelector}'
    Expected output 
    {"matchLabels":{"release":"kps"}}

    This Prometheus only reads ServiceMonitors labelled release: kps. Yours has no labels, so for this Prometheus it does not exist. It is the same rule as a Service selecting Pods, and the operator's own troubleshooting guide lists it as the first thing to check: are the ServiceMonitor's labels inside what the Prometheus object selects?[5] It is the most common "my target never shows up" bug with this chart.

    The fixed version is in the file you copied. The only difference is the label:

    monitoring/servicemonitor-podinfo.yaml

    apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: podinfo
  namespace: default
  labels:
    release: kps
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: demo-podinfo
  endpoints:
    - port: http
      path: /metrics
    kubectl apply -f monitoring/servicemonitor-podinfo.yaml
    genconf | grep 'job_name: serviceMonitor/default'
    Expected output 
    servicemonitor.monitoring.coreos.com/podinfo configured
- job_name: serviceMonitor/default/podinfo/0

    In our run the new job was in the generated config 2 seconds after the apply. The same name, podinfo, so apply updated the object instead of creating a second one. Delete the first-try file: rm monitoring/sm-first-try.yaml.

  4. See the operator's side of it:

    kubectl -n monitoring logs deploy/kps-operator --tail=5
    Expected output (one of the lines; timestamps differ) 
    ts=... level=info caller=/workspace/pkg/prometheus/server/operator.go:907 msg="sync prometheus" component=prometheus-controller key=monitoring/kps-prometheus

    sync prometheus is one turn of the control loop: read all selected ServiceMonitors, render the config, write the Secret.

  5. Wait, and do nothing. Refresh Status → Target health every 15 seconds, or use the terminal:

    curl -s localhost:9090/api/v1/targets | jq -r '.data.activeTargets[] | select(.labels.job=="demo-podinfo") | "\(.scrapePool) \(.health) \(.scrapeUrl)"'
    Expected output (your IP differs) 
    serviceMonitor/default/podinfo/0 up http://10.244.0.8:9898/metrics

    You get one such line per podinfo Pod: with two replicas, a second line with the other Pod's IP.

    In our run the target was up 57 seconds after the apply. Why not 2 seconds? The Secret is mounted into the Prometheus Pod, so the same kubelet sync delay from part A applies. What is different: you did not exec, you did not curl /-/reload. The config-reloader sidecar noticed the new file and reloaded Prometheus for you.

    And look at the addresses: Pod IPs, one target per Pod. The ServiceMonitor follows the Service's EndpointSlices, so Prometheus knows each Pod separately. Scale podinfo to three and a third target appears, with no edit anywhere.

Do it, part C: switch the operator off

An operator is just a program in a Pod. What happens when it is not running? Lesson 02 predicted it: the desired state is stored, but nothing acts on it, until the loop comes back and compares again. That is level-triggered: the operator reacts to how things are when it looks, not to the events it missed.[6]

  1. Start clean: delete the ServiceMonitor, then stop the operator.

    kubectl delete -f monitoring/servicemonitor-podinfo.yaml
    kubectl -n monitoring scale deploy/kps-operator --replicas=0
    kubectl -n monitoring get deploy kps-operator
    Expected output 
    deployment.apps/kps-operator scaled
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
kps-operator   0/0     0            0           113s

  2. Apply the ServiceMonitor again, with the right label this time.

    kubectl apply -f monitoring/servicemonitor-podinfo.yaml
    kubectl get servicemonitor podinfo
    Expected output 
    servicemonitor.monitoring.coreos.com/podinfo created
NAME      AGE
podinfo   0s

    The object exists. The API server stored it, as it stores any object. Wait 30 seconds and check the generated config:

    genconf | grep 'job_name: serviceMonitor/default'
    Expected output 
    (no output)

    Empty. Your ServiceMonitor is correct and stored, and nothing happens, because nobody is watching it. The CRD gave the API a new noun. Only the operator gives it a meaning.

  3. Switch the operator back on.

    kubectl -n monitoring scale deploy/kps-operator --replicas=1
    kubectl -n monitoring rollout status deploy/kps-operator
    genconf | grep 'job_name: serviceMonitor/default'
    Expected output 
    deployment.apps/kps-operator scaled
deployment "kps-operator" successfully rolled out
- job_name: serviceMonitor/default/podinfo/0

    Within seconds of starting, the operator caught up. It never saw the "ServiceMonitor created" event; it was not running. It did not need to. On start it compared what is with what should be, and fixed the difference. Level-triggered, in action.

  4. Drift, part 1. Delete the generated config:

    kubectl -n monitoring delete secret prometheus-kps-prometheus
    kubectl -n monitoring get secret prometheus-kps-prometheus

    It is back, with an AGE of a second or two. In our run it was recreated after 1 second. Any hand edit to that Secret meets the same fate: the next sync overwrites it from the CRs.

  5. Drift, part 2. Scale the Prometheus StatefulSet itself to zero, as if someone "temporarily" turned it off:

    kubectl -n monitoring scale statefulset prometheus-kps-prometheus --replicas=0
    kubectl -n monitoring get statefulset prometheus-kps-prometheus
    Expected output, about 5 seconds later 
    NAME                        READY   AGE
prometheus-kps-prometheus   0/1     ...

    0/1: the operator has already set the desired count back to 1, because the Prometheus CR says one replica. A few seconds later it is 1/1 again. The source of truth is the CR, not the StatefulSet.

    This restarted Prometheus, so your 9090 port-forward died with the old Pod. Stop it with Ctrl+C and run it again.

  6. Keep monitoring/servicemonitor-podinfo.yaml and commit it with the copied files. Leave the stack and podinfo running; the next lesson builds on them.

    git add monitoring/
    git commit -m "Scrape podinfo with a ServiceMonitor"

The comparison

You have now done the same job both ways. Here it is side by side:

Config file (traditional)Operator (ServiceMonitor)
Who writes the scrape configYou, by hand, in one shared fileThe operator, generated from many small CRs
OwnershipOne file that every team edits: merge conflicts, one ownerEach team ships its own ServiceMonitor next to its Deployment
TargetsStatic host:port, here a Service: one target for two PodsLabel selector on Services, follows the Pods: one target per Pod
ValidationNone at apply. A typo shows up at reload, or at the next restartThe API server checks the CR against its schema at apply
ReloadYou trigger it, and must not forgetThe config-reloader sidecar does it
LifecycleApp deleted, its job stays in the file until someone removes itDelete the ServiceMonitor, the job disappears
DriftA hand edit stays until someone noticesThe operator puts it back to match the CR
CostNothing extra runningOne more program that must be running, and can fail
DebuggingRead the one fileRead the CR, then the operator log, then the generated config

Honest about speed. The operator did not make the target appear much faster: 57 seconds against about 61 plus your reload. Both wait for the kubelet to sync a mounted volume. Speed is not the win. The win is everything around it: no manual reload to forget, a schema that rejects some mistakes at apply, a ServiceMonitor each team owns, targets that follow Pods, and a loop that heals drift.

Honest about cost. An operator moves the work from "edit a file" to "trust a program". You saw what that means in part C: when the program is off, correct objects silently do nothing. In part B you saw the other face of it: a ServiceMonitor with the wrong label also silently does nothing. Debugging has one more layer: the CR, then the operator's log, then the generated config. That is the price. For a stack that many teams change every week, it is usually worth paying. For one small app with one config file that never changes, it may not be.
