Make your server twelve-factor

Your win: a server that meets all twelve factors. It counts its visitors in a shared backing service, runs as two replicas on your kind cluster, shuts down without dropping a request, and passes the self-check script.

Before this: Session 1 and its lessons, especially the twelve-factor table in lesson 02. Your 20-line server meets about seven of the twelve factors. This homework closes the gap. Everything you need that the lessons did not cover is in New for this homework below.

How to submit

  1. In your hello repository, create a branch: git switch -c hw1-twelve-factor.
  2. Do the work, commit, push the branch, and open a pull request into main.
  3. Paste the full output of the self-check script into the pull request description, and request your instructor as reviewer.
  4. Deadline: before session 2. Your instructor reviews between sessions and may ask for changes. Answer the review comments in the same pull request.

What to build

The self-check script talks to your server, so the interface below is fixed. How you build it inside is up to you.

HTTP endpoints

RequestResponse
GET /Increments a visit counter stored in Redis and answers <greeting> (visit <n>, served by <hostname>), e.g. hello from the cluster (visit 7, served by hello-6d9f…). If Redis is unreachable, answer 503.
GET /healthzok. It must work even when Redis is down: is the process alive?
GET /slowWaits 3 seconds, then answers 200. It exists only so the check can prove a graceful shutdown.

Configuration (environment only)

Behaviour

  • Admin process: running the same binary with the single argument reset sets the visit counter back to zero and exits 0. It does not start the server.
  • Logs: one JSON object per line on stdout, nothing on stderr. One event per request, including at least the method, the path and the status.
  • Shutdown: on SIGTERM, stop accepting new connections, let requests already in progress finish, then exit 0.

New for this homework

These are the pieces the session 1 lessons did not cover. Each one comes with the primary source to read.

1. A dependency

Add the official Redis client with go get github.com/redis/go-redis/v9. It updates go.mod and writes go.sum, the checksums that pin exactly what you downloaded. Commit both.[1] Start from the client's Getting started guide: redis.ParseURL turns REDIS_URL into options, and Incr is an atomic counter.[2] In the Dockerfile, copy go.mod go.sum and run go mod download before copying your code. That is the cache trick from lesson 04, and now it saves real time.

While you develop, run Redis on your laptop in a container. Its port is published on localhost:6379, so go run . finds it with the default REDIS_URL:

docker run -d --name redis -p 6379:6379 redis:8-alpine
docker exec redis redis-cli ping
Expected output 
PONG

Stop it with docker stop redis to see your 503, start it again with docker start redis, and remove it with docker rm -f redis when you are done.

2. Redis in the cluster

k8s/redis.yaml holds a Deployment and a Service, with the same shape you wrote in lesson 07. Two YAML documents can share one file if you separate them with a line containing only ---. Inside the cluster, a Service's name is also its DNS name, so your server reaches Redis at redis://redis:6379/0.[3] Losing the counter when the Redis pod restarts is fine for this homework.

3. Environment variables in a Deployment

Each container in the pod template can carry an env list:[4]

env:
  - name: GREETING
    value: hello from the cluster

4. Probes: startup, readiness, liveness

The kubelet keeps asking your container questions, and a probe is one of those questions. Kubernetes has three kinds, and each failure leads to a different action:[11]

ProbeThe questionWhen it fails
startupHas the app finished starting?After failureThreshold misses the container is restarted. Until it succeeds, the other two probes do not run at all.
readinessShould this pod get traffic right now?The pod's IP is removed from the Service. Nothing is restarted, and it gets traffic again once it passes.
livenessIs the process stuck beyond repair?The container is restarted, with SIGTERM first, so your graceful shutdown runs.

Every probe has the same timing knobs.[11] periodSeconds (default 10) is how often it asks. timeoutSeconds (default 1) is how long one answer may take. failureThreshold (default 3) is how many misses in a row count as failure. initialDelaySeconds is how long to wait before the first question. A startup probe gives a slow app failureThreshold × periodSeconds to come up: 30 × 10 is a 5-minute budget, for example.[5] Without a startup probe, the only way to protect a slow starter is a long initialDelaySeconds on liveness, which also delays catching real failures.

Your server starts in milliseconds, but you still configure all three in k8s/deployment.yaml, all against /healthz on port 8080:

startupProbe:
  httpGet:
    path: /healthz
    port: 8080
  periodSeconds: 1
  failureThreshold: 10
readinessProbe:
  httpGet:
    path: /healthz
    port: 8080
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080

Here is what each failure really looks like. These are three pods whose probe points at port 9999, where nothing listens, observed for 40 seconds on kind:

kubectl get pods 
NAME         READY   STATUS             RESTARTS      AGE
ready-demo   0/1     Running            0             40s
live-demo    0/1     CrashLoopBackOff   3 (14s ago)   40s
start-demo   0/1     CrashLoopBackOff   3 (4s ago)    40s
kubectl events (one line from each pod) 
Warning  Unhealthy  Pod/ready-demo  Readiness probe failed: Get "http://10.244.0.8:9999/healthz": dial tcp 10.244.0.8:9999: connect: connection refused
Normal   Killing    Pod/live-demo   Container hello failed liveness probe, will be restarted
Normal   Killing    Pod/start-demo  Container hello failed startup probe, will be restarted

ready-demo never restarts. It only drops out of the Service, and kubectl get endpointslices -l kubernetes.io/service-name=hello lists it with ready=false. The other two restart until they back off.

The classic mistake: a liveness probe that checks a dependency. If /healthz asked Redis and Redis went down, every replica would fail liveness and be restarted over and over, and restarting your server fixes nothing about Redis. Liveness asks about this process only. If you ever want "Redis is down, stop sending me traffic", that belongs in readiness, never in liveness.

5. Structured logs, and libraries that log

Go's log/slog package writes JSON with slog.NewJSONHandler(os.Stdout, nil). Make it the default logger, and log one event per request from a small wrapper around your handler.[6] Watch out: libraries log too. When Redis is unreachable, go-redis prints its own lines to stderr unless you hand it a logger with redis.SetLogger.[7] The self-check catches this, so check your stderr.

6. Graceful shutdown

When Kubernetes stops a pod, it sends SIGTERM and waits a grace period, 30 seconds by default, before it kills the process.[8] Use that time. signal.NotifyContext gives you a context that is cancelled on SIGTERM.[9] http.Server.Shutdown stops accepting new connections and waits for running requests to finish.[10] This means you need an http.Server value instead of the bare http.ListenAndServe.

7. A one-off admin process

Read os.Args. If the first argument is reset, clear the counter and return before the server starts. In the cluster, run it as a temporary pod from the same image and the same config:

kubectl run reset --rm -it --restart=Never --image=hello:0.2.0 --env=REDIS_URL=redis://redis:6379/0 -- reset

8. Getting the image into kind

No registry yet; publishing images comes in session 2. Build and load it exactly as in session 1, with the new version tag:

docker build -t hello:0.2.0 .
kind load docker-image hello:0.2.0

Self-check

Deploy your work from your hello folder:

kubectl apply -f k8s/

The check script is in the course repository you cloned in the pre-flight check. Go to that folder, update it, and run the script against your image:

git pull
bash scripts/check-12factor.sh hello:0.2.0

Questions your reviewer will ask

A green check proves the behaviour. Review checks that you understand it. Expect questions like these in your pull request or at session 2, and be ready to explain every line you submit:

  1. Why does /healthz not ask Redis? What would happen to your two replicas if it did, and Redis went down?
  2. A pod is deleted while it answers /slow. Walk through what Kubernetes and your code do, second by second.
  3. You scale to five replicas. Why does the count stay right, and what would break if the counter were a Go variable?
  4. Redis now needs a password. Where does it go, and where must it never go?
  5. Why is reset a separate one-off process and not an HTTP endpoint?
  6. What is in go.sum, and why is it committed?
  7. Which factor was hardest to meet, and which one does your README mark as "not applicable"?

Not required

Redis persistence, Redis passwords, high availability, Helm, CI: all of that comes later or is out of scope. Keep it small and correct.
