Homework 2 · between session 1 and session 2 · about 60–90 minutes

Fault hunt: bring a broken deployment back

Your win: you take over a Deployment and a Service that do not work, find eight faults by reading what Kubernetes tells you, fix each one in a file, and can prove every diagnosis with one line of real output.

Before this: lessons 05 to 08, and the image hello:0.1.1 you built in lesson 07. This homework teaches nothing new. Every fault is something a lesson showed you, now without the lesson telling you where it is.

The story

Monday morning, you are on call. On Friday afternoon a colleague shipped hello to a fresh cluster, wrote "deployed, all good" in the team chat, and left for a week of hiking with no signal. Since then nobody has managed to reach the service. Their two manifests are all you have. Make it work, and leave a report so the colleague learns what went wrong.

How to submit

  1. In your hello repository, create a branch: git switch -c hw2-fault-hunt.
  2. Set up the cluster (below), hunt, commit fault-hunt/, push the branch, and open a pull request into main.
  3. Paste the full output of the self-check script into the pull request description, and request your instructor as reviewer.
  4. Deadline: before session 2, the same as homework 1.

The rules

  • There are exactly eight faults: six in deployment.yaml, two in service.yaml. One fault can hide the next, so fixing one may reveal another.
  • Fix the files, then kubectl apply -f fault-hunt/. You may try a change live with kubectl edit, but the self-check fails until the files match the cluster.
  • Repair, never remove. The Deployment keeps 2 replicas, a memory limit and all three probes. Deleting a probe hides a fault; it does not fix it, and the self-check catches it.
  • Look before you change. For every fault, find the line of output that names the cause before you touch a file. That line goes into your report.
  • No hints. Everything you need is in what kubectl prints.

Set up

The setup script creates a separate one-node kind cluster called fault-hunt, so your lesson cluster stays untouched. It copies your hello:0.1.1 image into the cluster, copies the broken manifests and a report template into fault-hunt/ in your repository, and applies them. Before you run it, start Docker (Docker Desktop, or the Docker service on Linux) and wait until it is running: docker info must answer without an error. kind runs the cluster inside Docker. Then get the latest course material:

git -C ../kubernetes-and-devops pull

Then, from the root of your hello repository:

bash ../kubernetes-and-devops/scripts/fault-hunt-up.sh

The commands assume your hello and kubernetes-and-devops folders sit side by side. If not, adjust the ../kubernetes-and-devops path. No hello:0.1.1 left? Rebuild it from that commit, or pass another image that has no backing service: … fault-hunt-up.sh hello:0.1.0.

Expected output (the end) 
Copied the manifests and REPORT.md into fault-hunt/.
deployment.apps/hello created
service/hello created

Your kubectl now points at kind-fault-hunt. The hunt is on: kubectl get pods
Back to your lesson cluster later: kubectl config use-context kind-kind

The script is safe to run again, for example after a reboot: it reuses the cluster, keeps your edited files and applies them.

The method

Every fault in this homework follows the same loop. Do not skip steps, and do not guess:

  1. Look: kubectl get pods, kubectl get deploy,rs,svc,endpointslices. Which object is not in the state you expect?
  2. Ask that object: kubectl describe it, and read State, Last State, Conditions and the Events at the bottom.
  3. Ask the process: if a container started, kubectl logs it; if it already died, kubectl logs --previous.
  4. Compare: what the YAML asks for against what exists. kubectl get … -o yaml shows the full truth.
  5. Change one thing in the file, kubectl apply -f fault-hunt/, and go back to step 1.

The commands you need all come from lessons 05–08:

QuestionCommand
What runs, and in what state?kubectl get pods, kubectl get pods -w
Why is it in that state?kubectl describe pod <name>, kubectl get events --sort-by=.lastTimestamp
What did the program say?kubectl logs <pod>, kubectl logs <pod> --previous
Is the rollout stuck?kubectl rollout status deploy/hello, kubectl get rs
Where does the Service send traffic?kubectl get svc -o wide, kubectl get endpointslices
Which images does the node have?docker exec fault-hunt-control-plane crictl images
Does it answer?kubectl port-forward svc/hello 8080:80, then curl localhost:8080/
Do my files match the cluster?kubectl diff -f fault-hunt/

After each fix, old broken Pods may linger next to the new ones. That is the rollout at work (lesson 07): with 2 replicas it adds one new Pod at a time and removes an old one only when a new one is ready. Always read the newest Pod: kubectl get pods --sort-by=.metadata.creationTimestamp.

The report

The setup script created fault-hunt/REPORT.md with eight empty sections. Fill in one per fault, in the order you found them:

FieldWhat goes in it
SymptomWhat you saw first, e.g. the STATUS column.
CommandThe command whose output showed you the cause.
EvidenceThe exact line of that output, copied, not retyped.
CauseOne sentence: what was wrong, and why it produced that symptom.
FixThe file and field you changed, and the value you chose.

The report is what gets graded. The fixed YAML alone proves little, because anyone could compare it with the lessons. The evidence line proves that you found the fault by looking.

Check your work

From the root of your hello repository:

bash ../kubernetes-and-devops/scripts/check-fault-hunt.sh

It checks only outcomes: Pods scheduled and running, no restarts for 40 seconds, ready endpoints behind the Service, an HTTP 200 through it, and files that match the cluster. It never names a cause, so a red line tells you where to look, not what to change. It takes about a minute, and it changes nothing.

Run it right after setup too. It passes a few checks at once, because a broken system can look partly fine; the failing ones are your starting point.

Clean up

When the pull request is open, delete the cluster and point kubectl back at your lesson cluster:

kind delete cluster --name fault-hunt
kubectl config use-context kind-kind

Your fixed files stay in your repository. To hunt again later, run the setup script: it recreates the cluster from them.

Questions your reviewer will ask

  1. Two of the faults crash-loop. How did you tell them apart, and which command did that?
  2. While a Pod was Pending, why was there no image pull error, even though the tag was also wrong?
  3. The Service's own fields looked fine to kubectl get svc. What showed you that it sent traffic nowhere, and later to the wrong place?
  4. While you fixed the Deployment, old broken Pods stayed around. Why did Kubernetes not remove them at once?
  5. Which memory limit did you pick, and how would you choose one for a real service?
  6. Your colleague wrote "all good". Which one command could they have run on Friday to see it was not?

Stuck? Run the method again from step 1 on the newest Pod, and read every line of describe. Still stuck? Ask your instructor, with the self-check output and the describe output.
